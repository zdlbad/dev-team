# 写代码的角色共守的 — 原型与编码

规范在 [coding-standard.md](coding-standard.md)（能不能解码，硬）与 [style.md](style.md)（读着顺不顺，软；冲突时编码规范为准）。本文是两个写码角色共用的做法。

## 先补关键逻辑，等人确认，再写

读 `plans/<id>.md`。每个标「待补」的步骤，在 `keyLogic` 里写这一步守哪条规则、哪条不变量在这里生效、`when` 分流怎么走、哪条五问的回应在这里落地（「连点两次确认，第二次在 status 守卫处抛 OrderFailed」）；外壳步骤写事务边界在哪、乐观锁怎么落（`where version = ?`）、哪个错误映射哪个状态码。**补完停下**，等人 `plan confirm`。开写前读计划里「人在步骤上留的话」（`plans/<id>.md` 那一节，或步骤的 `humanNotes`）：人对哪一步有话就按话改，`plan done` 的说明里回一句改了什么。

**关键逻辑只写模型没说的那部分**（2026-09-15 项目所有者定）。

守卫的顺序、每个守卫抛什么、按领域结果怎么分流、每一步调谁——**这些模型里全有**，人在「审模型」页已经逐条确认过，方向 ②（审代码对模型）还会拿解码回来的模型跟设计模型机械比对：少一个 throws、少一步、签名不一样，都是错误级。**写进关键逻辑等于让人把同一批守卫读第二遍**，计划页因此又长又像模型页。

所以关键逻辑只留四类——都是模型表达不了、方向 ② 也看不见的：

1. **边界语义**：模型规则写「落在最低价与最高价之内」，代码写 `<` 还是 `<=` 解码回来文字一样，② 照样通过。这类必须写：「两头的边界算落在里面」。**写的时候顺手想一下：这句话是不是其实该写进模型的规则里？** 是的话报给模型师，写进模型比写进计划好——那样人确认一次、机器永远核得住。
2. **实现决定**：防御性拷贝、id 谁生成、version 从 0 起、`FROM_PERSISTENCE` 一道守卫不走、字符串修不修剪。
3. **测试这一步断言什么**：校验的明文盲区，只有 pre-pr 的 D 角度查。
4. **改动步骤的原因与处理办法**（见下）。

一步如果这四类一条都没有——比如「按模型建一个值对象」——**关键逻辑就留空**，不必为了填而填；人在计划页上只看有话说的那几步。

两种形状，看这一步是新建还是改动。两种都不写你的思考过程——人要看的是「这一步会发生什么、为什么」，不是你怎么想到的。

### 新建一个文件：写清单

一行一步，按执行顺序排，每行说**做什么**与**为什么**。只写上面那四类；模型里已有的守卫与抛错不写。

```
1. 五样填没填、读不读得出来 → 缺一样 throw InvalidServiceAgreement // R-043
2. 议定的价比区间，两头的边界算落在里面 → 出界 throw InvalidServiceAgreement // R-091
3. 五样照填的原样记下，return 新的值对象
不动：档名是不是那五档之一（还没有法定名）；三个抄来的价在不在价目表上（本段不建价目表）
```

- **一行一件事**，按执行顺序；真要写结果就写 `→ throw X` / `→ return` / `→ raise E`，编号放行尾 `//` 后。
- 字段名单、参数名单要写全——人看计划时不该被迫同时开着模型。
- **写目的，不写辩解**。「缺一样就不立」是目的；「照 XxxService 的样子写」「因为聚合只能信参数全不全，所以……」是你的思考过程，不写。
- **「不动」一节只列名字**，一行一个，**不解释为什么不动**——那件事真要说，它已经写在模型的规则或 note 里了。
- **不复述模型规则原文**（人已经确认过模型），不抄注释怎么写、不说照哪个类的样子写、不写沿革。
### 改动一个已有的文件：写自然语言

增量步骤（给已有的类加一个行为、给已有的处理器补一步、改一个字段的类型）不写清单——清单看不出这次动了什么。用几句话说清三件事：

1. **为什么改**：哪条业务语句、哪次裁定、哪个报告要求的（「人裁 c3 之后复核日改成按服务起始日算」）。
2. **怎么处理**：动哪个方法的哪一段，从什么变成什么；旧的行为怎么办（保留、作废、调用方跟着改）。
3. **不动什么**：这一步碰得到、但这次不碰的东西，一行列完。

说人话、落到具体的人和事上，不摆条目符号也行；照样不写「照某某类的样子写」「因为……所以……」这类你的推理。

### 两种共同的

- 超过 600 字 `plan check` 只提醒，不拒收（2026-09-13 项目所有者取消了 300 字硬门禁）；**到了 600 字多半是在写思考过程**。字数按 JavaScript 字符数量，空格与换行都算：不要为了对齐编号补空格。
- 短是砍掉重复与推理砍出来的，不是砍内容：属于那四类的，该说全的说全。

**按计划顺序写**。每完成一步 `node $DEV_TEAM/tools/plan.js done <项目目录> <切片id> <n>`——顺序与计划不一致 `plan check` 会报。不「先写了再说」绕过命名规则或计划顺序。

## 让代码可解码：模型到代码的对应

| 模型 | 代码 |
|---|---|
| `traces` | 类 / 方法 JSDoc 的 `@trace G-001 R-001` |
| 聚合不变量 | 类 JSDoc 的 `@aggregate-invariant [R-xxx] 文本` |
| 根 / 实体 / 值对象的 `invariants` | 类 JSDoc 的 `@invariant [R-xxx] 文本 {ErrorName}`（花括号是创建时违反抛出的错误） |
| 行为 / 领域服务操作的 `rules` | 方法 JSDoc 的 `@rule 文本`，一条一行 |
| 行为的 `raises` / `throws` | 方法体里 `this.raise(new XxxEvent(...))` / `throw new XxxError(...)`；解码器沿调用链传递 |
| 工厂 | 静态方法，全大写蛇形：`CREATE`、`FROM_PERSISTENCE` |
| 用例步骤 | 处理器 `execute` 体内每条语句上方的 `//` 注释 = 步骤文本；`if` 上方的 `//` = `when` |
| 用例 `actor` / 事件处理的 `trigger` | 处理器类的 `@actor` / `handle` 方法的参数类型 |
| 聚合叙述 `aggregateNarrative` | 聚合根类的 `@narrative` |
| 错误的 `condition` | 错误类的 `@condition`（不解码，只为人读） |
| `idRefs` | `props` 里持有其它聚合 id 的字段加 `@ref Module.Aggregate` |
| 端口 | `port.<Name>Interface.ts` 的接口 + `@external-system` 或 `@module` |
| 模块职责 | `module.ts` 的 `@responsibility` |

事件在聚合里 `raise`，由应用层在**最后一步** `publish`。仓储读写只看方法名前缀（`find*` / `exists*` / `count*` 是读，其余是写）。全表见编码规范「结构化注释」「解码规则汇总」。

## 领域代码的纪律

- 处理器里不出现业务 `if`（比较输入、字段、数值）、不直接 `throw` 领域错误（用 `assertFound` 之类的守卫，或让聚合抛）、不计算（哪怕一次加法）——判断属于聚合行为或领域服务，处理器只按领域调用的结果分流。
- 适配器只做线格式转换，不含任何业务判断；不为了跑通而在适配器里塞判断。
- 组合根只做装配：适配器 → 领域服务 → 处理器 → 事件订阅；是唯一允许 `new` 适配器的地方。
- 注释按编码规范「注释写什么」：讲代码的行为和原因；类上只说这个类守的规则，要提示别处守的最多一句「唯一性不由这里守」；上下文不必写全，模型的 `note` 不照抄进代码（第八十七批）。
- 不写模型没有的公共行为（私有辅助方法可以，解码器不看私有）。
- **模型有明显错误**：报告，不改；等模型师改完再继续。

## 动已经确认过的步骤，那一步的确认就作废

人确认的是他当时读到的那段关键逻辑。你事后改了那一步的 `keyLogic`，**他的确认就挂在变过的话上，不算数了**——工具认得出来（确认时记下了当时的文字）：`plan check` 会报「确认之后关键逻辑被改过」，`plan done` 不让开写，计划页那张卡会写「你 X 月 X 日确认之后，关键逻辑被改过——上面是新的文字，看过再确认一次」。所以改完**交回开发指挥并说清改了哪几步**，由它请人重看那几步，别当没事发生。（2026-09-15 真出过：十八步全确认之后，十步的关键逻辑被重写，计划照旧显示已确认。）

## 计划确认之后人又裁了一条

在**原有步骤里**补守卫、补用例，把新规矩写进那几步的 `keyLogic`（`plans/<id>.json`，`.md` 跟着改成一样），别新开一步。**不要跑 `plan build --force`**（会把人的确认与完成记录清零），**不要手改 `modelFingerprint`**（那是防计划过期的闸门）。改完把情况交回开发指挥，由它跑 `plan amend` 核对后换指纹（2026-09-13 第七十三批）。

## 自检

```
node $DEV_TEAM/tools/decode.js <代码库> <临时目录>                       # 解码；临时目录放项目的 model-decoded/ 下
node $DEV_TEAM/tools/diff-model.js <项目目录>/model <临时目录>             # 粗比对，写的时候用它盯自己这一层
node $DEV_TEAM/tools/validate.js <项目目录> --code <代码库> --slice <切片id>  # 真正的关卡（方向 ②）；交回前以它为准
node $DEV_TEAM/tools/plan.js check <项目目录> <切片id> --code <代码库>      # 文件都在、顺序一致、walk.input 齐
node $DEV_TEAM/tools/test.js <代码库> <片段>                              # 一小批测试；不带片段是整套，慎用
```

**两个比对工具口径不一样，别拿错的那个当准。** `diff-model.js` 是粗比对，模型上的说明文字（`note`）、住在成员值对象上的 `idRefs` 它都当差异报；`validate.js` 的方向 ② 才是关卡，按第八十七批不把 `note` 算差异。写的时候用 `diff-model` 盯自己这一层方便，**但交回前一定以 `validate` 为准，报告里写它的数**——别去追关卡根本不管的差异（2026-09-15 s-003 真出过：`diff-model` 报 4 条，关卡只有 2 条）。

每层写完自跑解码比对，差异为 0 再进下一层。解码器报的 lint（处理器里的业务判断、直接 throw、漏 publish）必须清零。产出里附最后一次比对、`plan check` 与测试的结果行。
