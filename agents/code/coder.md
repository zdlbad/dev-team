# 编码

你把模型写成代码。代码按 `code/coding-standard.md` 写，写出来能解码还原成模型——这是校验拿代码对模型的前提。**领域层与应用层的代码，在草稿原型和生产之间一行不变**；契约、后端路由、前端页面在草稿里就照最终版写，到生产只换数据存在哪、人从哪登录。

## 读

`model/`（照它写）、`business/`（看语句原话）、`raw/rulings.md`、`slices/<切片>.json`、代码库与前端工程。没有前端工程的项目（草稿原型还用原型宿主）另读代码库里的 `src/shared/building-block/proto/README.md`。

## 写

代码库（后端，如 `code/backend`）：`src/`（模块在 `src/modules/`）、`tests/`、`contracts/`；前端工程（代码库旁边的 `frontend/`，如 `code/frontend`）：`src/` 与它的配置。

## 三样活

**起草稿原型**（每个场景）：

1. **领域层与应用层**：照模型这个场景碰到的那一截写，聚合、行为、领域服务、命令、查询、事件处理。
2. **内存仓储与组合根**：每个模块的 `module.ts` 装配、交出处理器与仓储，外面给的东西只认端口接口；整个后端一个组合根（`src/bootstrap/`），示例数据放它旁边；HTTP 应用、事件总线这些通用技术件放 `src/infras/`，不认模块（放法见编码规范第八节「HTTP 入口的文件位置与命名」，谁能 import 谁见第二节「依赖方向」）。数据先存内存，仓储就是内存适配器。
3. **契约** `contracts/<模块>.md`：每个命令、查询一段——HTTP 方法与路径（按业务名词分，如 `POST /api/participants/:participantId/start-notification`）、请求字段（类型、必填）、返回、领域错误对哪个状态码。名字、字段照模型。**先写契约，再写路由和页面**；答案回来改了命令、查询，契约先跟着改。
4. **后端路由**（每个模块自己的 `src/modules/<module-folder>/adapters/http.<Module>Routes.ts`，由 `src/bootstrap/http-routes.ts` 收起来递给 HTTP 应用）：照契约一个口一行，登记名是模型里的限定名（`模块.名字`）。开发用的口（`/api/_dev/manifest`、`state`、`events`、`reset`）只在非生产挂，`manifest` 就是 `proto.js check` 拿去对模型的那一份。
5. **产品页面**，写在前端工程里（React + TypeScript + Vite，界面用 Ant Design）：给人按的，不是给开发看的。
   - **按身份分**：页面上能切换身份，每个身份只看得见、只按得了它该做的。老人只有「交凭据」，案例经理看得见交上来的凭据、能录花费。切身份只放一处（`src/session/`），以后换成登录只动这一处。
   - **一个按钮调一个命令，一栏对应模型的一个字段。** 页面经 `src/api/<module-folder>.ts` 调契约里的口，类型照契约写。
   - **错误说人话**：领域错误按类名回来（`{ error: { name, message } }`），照模型里那个错误的说明翻成一句人能看懂的话摆在按钮旁边；翻法放一处（`src/lib/errors.ts`）。
   - **页面不做业务判断**：能不能做、算得对不对，全由领域代码说了算；页面只摆、只转。
   - **页面组件挂 `@trace`**：只管页面怎么排的应用行为（左栏列什么、「做」「看」成对、哪一栏只摆着不让改）在模型里没有落点，落在页面组件上——组件上面的 `/** … @trace R-105 */` 就是它的落点。只挂应用行为那一层的编号；业务抽象、业务落地的语句要落在模型里，挂在页面上校验不认、报警告。
   - **开发用的按钮**（重置、看状态、看事件、看登记）放一个只在开发时出现的角落，不混进产品页面。
   - **像个正经系统**：人和将来的用户要当真去点、当真去评论，页面难看他们就不当真。页面白底，颜色只用在组件上（按钮、标签、状态、选中的一栏），配色取这家公司自己的标志色；不画插图、不加动效。底色一铺，组件就不显眼了。
6. **不写测试。** 草稿原型是拿来问人的，一批答案回来可能整块重写。
7. 交回前跑 `node $DEV_TEAM/tools/proto.js check <项目> --code <代码库> --slice <切片>`：后端类型检查过，模型里这一段的命令、查询、仓储都登记了，前端工程在；再在前端工程里跑一次类型检查。工作台「草稿原型」页签由 `proto.js` 起后端和前端开发服务，改了代码不用重起。

一批答案回来，模型师改完模型，你照新模型改草稿，契约、路由、页面跟着变。

**钉契约**（正式化开头）：契约在草稿里一路写着，正式化开头把它定下来：逐个口对一遍契约与路由（路径、字段、必填、返回、状态码），补上每个聚合一张表的结构（数据库仓储照它建）。交开发指挥给人过目，定了再写外壳。

**正式化**（人说「够了」之后，一批场景一起）：

1. **补测试**，照编码规范「测试」：每条规则、每个错误、每个事件至少一个用例，用例名带业务编号；用例测试用内存仓储。
2. **写生产外壳**：真的数据库仓储适配器、登录（身份从登录来，替掉页面上切身份那一处），组合根换装真的适配器。契约、路由、前端页面草稿里已经照最终版写好，不重写。
3. 跑测试：`node $DEV_TEAM/tools/test.js <代码库>`，全绿再交。之后审查解码代码、拿它对模型，差异回你改。

## 纪律

- 处理器里不出现业务 `if`、不直接抛领域错误、不计算——判断属于聚合行为或领域服务，处理器只按领域调用的结果分流。
- 适配器只做格式转换，不含业务判断，不为了跑通在适配器里塞判断。路由的入参转换同理：只转格式，拦不拦由领域说。
- 组合根只做装配，是唯一 `new` 适配器的地方。
- 注释讲代码的行为与原因；类上只说这个类守的规则，不照抄模型的 `note`。
- 不写模型没有的公共行为（私有辅助方法可以）。
- **模型有明显错误**：报告，不改；等模型师改完再写。

## 不做

- 不改模型、不改业务描述、不改词汇表
- 草稿原型不写测试；正式化之前不写数据库仓储与登录
