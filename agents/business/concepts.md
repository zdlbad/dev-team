# 全局图与概念

给人建立业务理解的三样东西里的两样（第三样是故事，`stories.md`）：先一张全局图看清这门业务分几块、块与块之间怎么交流；再一个概念一张，一个一个立住。都是讲业务，不是讲做法。核心资源怎么认、怎么拿它串起业务，见 `business/resources.md`。原来的业务框架、聚焦两种文章 2026-10-31 项目所有者定了不再写。

## 全局图

工作台「业务 › 全局图」。两层：**上一层**只画业务主题——一块一个主题，块里写主题名、两条主要发生的业务、几样数据；块与块之间的线上写主要的业务交流；**下一层**是一个主题里面——这一块的数据、角色、线，别的主题里连着的数据画成虚框、点了过去。画法在 `ui/guideline.md`「布局」一节（2026-10-31 定下）。

图不是人画的。**上一层由业务分析写在 `business/全局图.json`**（形状 `schema/map.schema.json`）——业务分几块、每块叫什么、按先后摆在哪、主要发生什么、块与块之间主要交流什么（人写的，不从细线数出来）：

```jsonc
{ "topics": [ { "id": "g2", "title": "参与者档案与她名下的钱", "does": ["建档、记下通知书", "记下分到资金那天"],
                "x": 1, "y": 0,                       // 格子位置：从左到右、从上到下是业务发生的先后
                "nodes": ["参与者档案", "她名下的基金"] } ],   // 这一块里的数据，写概念里节点的 title；次序就是块里从上到下的次序
  "edges": [ { "from": "g1", "to": "g2", "label": "批了什么、什么时候分到钱，记进她的档案" } ],
  "nudge": { "她名下的基金": 90 } }                      // 某一样手挪上下一截让开线，正数往下（ui/guideline.md）
```

**下一层从 `business/概念/*.json` 合并**，工具这样读概念：
- `kind: data` 的节点是数据，同名的并成一个（第一张给的 `sub` 算数；中间那个的不算）；有自己一张概念的框边粗一点，点了去概念页。
- 两头都是数据的线是主题里的线，同一对只取先出现的那条；线上的角色写在概念那条线的 `by`，上下层级（服务组 → 服务类型 → 服务）标 `tree: true`，全局图画成树。
- **角色 → 数据的线**把那个角色贴到数据框上（谁出的、谁管的）；数据 → 角色、角色 → 角色的线不进全局图，去概念页看。
- 概念里有、没划进任何主题的数据，和主题里点了名、概念里还没有的数据，页面底下各列一行提醒你补。

读原料时先划出来，场景走到还没有的一块再补。位置表达业务先后，不为了躲线交叉挪。

## 概念

`business/概念/<nn>-<概念>.json`，**一个业务概念一张**，业务分析写；工作台「概念」页照它画，人在页上按「定下」。这一页的作用是**说明业务概念**：它的定义、用大白话把定义讲明白、它跟别的东西什么关系。概念是**静态的**——它是什么、跟谁连着；怎么一步步发生的是故事（`stories.md`）。编号照全局图上出场的先后，两位数。项目所有者 2026-10-31 拿参与者、服务类型、服务三张小样定下的（内容范围和页面的样子都定了）。

一张上有什么，从上往下：

- **定义**：照手册、法规的说法一句，带出处；别的一方、别的文件上叫什么（一物多面）也写在出处里：「手册叫 participant；申报格式叫 care recipient；协议里是 you，说的都是这一个人」。
- **解释**：紧跟在定义底下一段，不带标签。大白话把定义讲明白，两三句：它在业务里管什么、钱从它身上怎么过、哪几件事定下来后面就照着来。
- **图**：它在中间，左边跟它有关系的角色和数据，右边它牵出的东西。**每条线上写的就是关系**（「批了她能用的服务类型」「跟她签协议、报入场、派照护伙伴」「名下有几笔，通知书定的」），不画事件、不标前因后果；指着线浮出一两句补充、出处、怎么一步步发生的在故事哪一步。中间框里列四五条要紧的事实名（编号、分级与路径、允许的服务类型、共付比例），指着看解释。
- **没有别的**：不写本质、类比、例子；不列纸上有哪些栏（模型师整理聚合设计的属性时直接读原料）；不写它的一生（那是故事的段和步骤）；图下不放表，不放说明文字。

**形状与颜色**：圆角淡蓝是角色，偏直角淡绿是数据，就这两种。中间那个也照它自己是角色还是数据（参与者圆角、服务偏直角），只是边框粗一点、摆在中间。

**一次认知消化量**（`seed/principles.md` 第 13 条，是指导不是规则）：一张图加一段简短的解释，这个量就差不多。关系多到一张图挤不下的，看看是不是两个概念混在一张里了；少到没东西学的，并进别的。

```jsonc
{ "title": "参与者",
  "definition": "照手册、法规的说法，一句",
  "definitionSource?": "§ 与行号；别的文件上叫什么也写这儿",
  "explain": "大白话讲明白定义，两三句",
  "nodes": [ { "id": "notice", "title": "决定通知书", "sub?": "评估代表寄来", "kind": "role|data", "side": "left|center|right",
               "facts?": [ { "name": "分级与路径", "text": "定她有哪几种基金" } ], "source?": "§6.6" } ],
  "edges": [ { "id": "1", "from": "notice", "to": "pt", "label": "写着她批了哪一级、哪条路径",
               "text?": "一两句补充", "story?": "<故事名> #<步骤>", "source?": "", "traces?": ["R-522"] } ],
  "questions": [] }
```

- `side: "center"` 的只有一个，就是这张讲的概念；`kind` 写它是角色还是数据。
- 线有编号，发了不改；聚合设计的 `refs` 写「<概念名> #<线>」。
- 原料没说、要人定的，写进 `questions` 并照「答问题」第 2 条发问。
- 人在页面上按「定下」，页面写 `confirmed`；之后内容再改，页面显示「改过」，等人重按。你改人已经定下的概念，交回里说一句改了哪几条线，开发指挥转给人重按。

**什么时候写**：聚合设计之前，主线上的概念先写一遍；场景定下后，这一段出现了还没有的概念，开发指挥先派业务分析「写概念」，再派模型师建模。
