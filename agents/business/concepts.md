# 业务框架、聚焦与概念卡

给人建立业务理解的三样东西，一层比一层细：先一份框架，看清这门业务的全貌；再一段业务一篇聚焦，把这一段展开；最后一个概念一张卡，一个一个立住。三样都是讲业务，不是讲做法。核心资源怎么认、怎么拿它串起业务，见 `business/resources.md`。

## 业务框架

`business/00-framework.md`，一个项目一份，业务分析写，在业务页上排第一篇。读原料时交；以后场景走进框架里还没有的一站，回头补上。全景 `business/00-overview.md` 照旧留着，是细一层的参考。

写三节：

1. **这门业务为什么存在**：它替谁解决什么，业务里有哪几方，核心资源从哪来、放在哪、往哪去。配两张图：各方之间谁给谁什么；核心资源怎么流，拿故事里的一笔走一遍。
2. **各方各自最想要什么**：一方一段话，说它是谁、最核心的目的、在这门业务里做什么。
3. **核心流程**：分阶段，每个阶段一段话说这时发生了什么，末尾一句本项目故事里的例子。配一张概念图。

分寸：

- **停在业务各方这一层**，像政府、老人、服务商这样的级别。一方内部的分工（服务商里谁录、谁批）是更细的一层，放到概念卡和场景里。
- **讲业务，不讲做法**：不写系统里的哪一步、哪个页面、谁点了什么。
- **手册的业务和我们公司的做法分开说**：讲的是原料上的业务；公司自己加的一道要说也标明「我们的做法」，另起一句。
- **先说业务，例子跟在后面**：先用业务的话说清这件事是什么、为什么，再拿故事里的人和数解释；例子不打头。
- **表最多两列**，格子里可以是一小段话；不为了整齐把话切成短句。
- **图用 mermaid**：写成 ```` ```mermaid ```` 代码块，业务页上画成图。概念图从左到右按概念出场的先后排，画成互相关联的网，不必是一条链；每条线写一句关系。画图工具照线的方向排左右，所以线顺着故事的先后往右连，往回作用的关系（报上去的钱回头从账户里扣、没花完的带进下一季）画虚线，左右才是出场的先后。

## 聚焦

`business/聚焦/<n>-<一段业务>.md`，框架核心流程里的一站或连着的几站一篇，业务分析写；也可以对着原料的一章聚焦（手册第 8 章护理管理、第 16 章申报与付款），三节照样写，文件名写章名。人说「聚焦到……」时写；场景走进还没有聚焦的一段，先写它再写概念卡。

**写法跟框架一样，三节**，只是下到这一段：

1. **这一段为什么存在**：它替这门业务解决什么，核心资源在这一段从什么状态变成什么状态；配一张图，把框架里资源流向图上落在这一段的那一截展开，拿故事里的一笔走一遍。
2. **几方与核心元素**：这一段有哪几方、围着哪几样东西转。**图先**：各方和元素画在一张图上，各方一种形状一种颜色（方框、浅蓝），元素另一种形状另一种颜色（双框 `[[ ]]`、浅黄），用 `classDef` 定两种样式；线写谁出它、谁拿它、谁回头看它，线上标先后的编号——一张图看出这几方是靠哪几样东西接起来的。**图下面一个列表**，先各方后元素，一项一段：各方那一段，框架里的三方到这一段展开一层（政府那边是哪几家各管一截、服务商这边是哪几层、老人身边还有谁），先说它最想要什么，再说它在这一段做什么，只展开这一段真出场的；元素那一段，它是什么（一句）、在这一段起什么作用、上面最要紧的几栏是哪几栏（只挑往后管事的，三五栏）、故事里的例子，有概念卡的指到卡（编号加名字）。元素只列核心的三五样，别把出场的全抄一遍；哪几样算核心，看钱从它身上过不过、后面的步骤要不要回头看它。
3. **核心流程**：分步，一步一段话，末尾一句故事里的例子；再配一张这一段出场的文件（概念）图，从左到右按先后。

**对一章聚焦**：章的边界跟框架一站重合的章（申报与付款、护理管理）写得顺；横跨好几站的章（预算）会一半篇幅在划边界，先跟开发指挥说一声，看是改成对一段业务聚焦还是照章写。

分寸同框架：讲业务不讲做法，表最多两列，图用 mermaid。**手册的业务和我们公司的做法分开说**：框架、聚焦、概念卡的本质讲的是原料上的业务——手册、法规怎么规定；这家公司自己加的那一道（裁定里定的财务复核、我们给自己的人也开发票）不是业务，要说也标明「我们的做法」，另起一句，不混进「业务里是这样」的句子里；钱的状态、流程的步骤，先照手册说，再说我们在哪一步加了什么。**先说业务，例子跟在后面**：每一节、每一段先用业务的话把这件事本身说清——它是什么、为什么这样——再拿故事里的人和数解释一遍；例子是解释业务用的，不拿它打头，不让读的人从数里自己猜业务。

## 概念卡

一个概念一张，挂在它出场的那一篇聚焦底下。概念是业务里的东西：一张纸、一笔钱、一件事，不一定是模型里的一个聚合。编号照框架概念图上出场的先后，两位数。一张卡两份文件、用同一个文件名，各有一个写的人，业务页拼成一张显示：

- `business/概念/<nn>-<概念>.md`，业务分析写：标题、在第几站出场、本质、类比、例子、图；是一张纸、一张单据这类实际存在的东西的，再写样子。
- `model/概念/<nn>-<概念>.md`，模型师写：细节，末尾一行模型里是哪个。

```
# 服务协议

在 ② 接收时签下，在 ③ 服务时每一次都从它取价，在 ⑤ 变化时改。

## 本质
## 类比
## 例子
## 图
## 样子

| 上面写着 | Sarah 的 | 对之后的业务有什么影响 |
|---|---|---|
```

```
## 细节

- 为了……，所以有……（属性）。
- 为了……，所以有……（行为）。

模型里：ServiceAgreement
```

一张卡从上往下读：在第几站出场 → 本质 → 类比 → 例子 → 图 → 样子 → 细节。

- **本质**：它是什么、业务里为什么会有它。第一句先说它在核心资源的流动上起什么作用。用业务的口吻、白话，贴着生活说，不用模型的词。**用中立的第三人称**：主语是业务里的各方——老人、服务方、照护伙伴、Services Australia、评估机构——不写「我们」「我们公司」；本质讲的是这门业务里这样东西是什么，谁来做都一样。具体的人名和「我们这家公司」留给例子。例：「决定通知书是政府给老人做完养老评估后的决定，写着她能得哪种服务、批到第几级；级别一定，她每年能用多少钱就定了。」
  **留意视角的切换（一物多面）**：同一样东西，站在不同的一方看，是不同的业务概念——Services Australia 眼里是「老人名下的账户」（它开的、它进出钱），服务方眼里是「老人的基金」（政府批给她、存在那个账户里、服务方看着别超支的钱）。写本质时先定站在谁的视角（通常是服务方），别的一方怎么叫它、拿它做什么，另起一句说清；两个视角混在一句里，读的人就分不清这东西到底在谁手里。这不是规矩，是写每张卡时要留的一个心眼。
- **类比**：别的行业里起同样作用的概念，一两句。例：决定通知书像保险公司的核保结论，写明这个人保不保、保额多少。
- **例子**：本项目故事里一个真实的情境：哪一天、谁、在哪、手里拿着什么、发生了什么，用演示案例里的人和数。
- **图**：画业务概念，不画细节。一张 mermaid 图，从左到右：它从哪来（谁给的、谁开的、谁往里放）→ 它本身——框里写它在业务上是个什么东西、由什么构成（账户按用途分几个、协议上一项一项服务各有价、申报一次服务一行），不列栏、不写字段 → 它往后牵着什么（哪几件事、哪几样东西靠它）。各方浅蓝方框、东西浅黄双框，样式同聚焦的图（`classDef party` / `classDef item`），线上写一句关系。一张图看出这样东西从哪来、是什么、往后牵着什么；哪一栏管什么事是样子表的事，不进图。图上也不画数目、频率、比例、怎么算的规则（每季一笔、留一成、季末结转、几样就几笔），不画流程步骤（先排队再分资金、攒起来再报），不画哪一方内部的分工（照护伙伴记、财务批）——这些分别归样子、聚焦的核心流程和细节。节点五六个就够，各方用业务那一层的名字（政府、老人、服务方）；一物多面的另一个叫法写在图题里一句。
- **样子**（只有实际存在的东西才有：政府寄来的通知书、签的协议、交上去的申报；「结转」这类事没有）：那张纸上对之后的业务有影响的栏一栏一行，照原料列，不只列模型存了的。三列：上面写着什么、故事里这一栏的值（原料没给的写「原料没给」）、这一栏对之后的业务有什么影响——它定了后面哪件事、后面哪一步要回头看它。只给人看、往后不管事的栏不一栏一行，合并成表末一行「只给人看：……」把名字列出来就够；几十栏的政府文件（付款对账单）尤其要这样收，表超过十来行人就读不动了。原料里有样纸的照样纸，没有的照原料列的内容。
- **细节**：模型里这个概念的每一栏、每个行为一句「为了……，所以有……」，标上属性还是行为，带上故事里的数；只是指着别处的几栏（跟哪位老人、在哪个网点）可以并成一句。规则不列。概念拆在别的元素上的（决定通知书拆在老人档案的几栏上），照样逐栏写，末尾写明落在哪个元素上。

**什么时候写**：场景定下后，这一段出现了还没有卡的概念，开发指挥先派业务分析「写概念卡」写前半张，再派模型师建模；模型师建完，把这一段加的栏和行为补进细节。已经有卡的概念这一段多了栏，模型师补一句。
