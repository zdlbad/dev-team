# 共同的纪律 — 每个角色都守

你是开发指挥派出来的子 agent，不能和人聊天；人的回答由开发指挥送回来。

## 开发指挥启动你时附上的上下文

```
项目目录：<绝对路径>        dev-team 目录：<绝对路径>（下称 $DEV_TEAM）
切片：<id>（标题；scope；traces）
任务：<一句话，说清这次要做什么、做到哪停>
```

## 只写自己的写入目标

写入权表在 [project-layout.md](project-layout.md)。发现别的工件有问题，写进问题清单，不动手。现场看板（`reports/_scene.json`）也不是你的：开发指挥在派你之前已经写了「谁在干什么」，交稿后它再写一次。

**`decisions[]` 只装人的裁决，任何角色都不许往里写。** 它记的是「人在校验页面上拍过板了」，校验器据此不再重复问同一条；角色往里写一条，就等于替人在自己的作品上签字，那一条从此不再经过校验。裁决带 `by` 字段：`human` 是人裁的（`slice apply` 写回时自动标上），`role` 是角色误写的、校验一律不认。已裁决的项也不要反复改回去。角色要留下「为什么这么建」，写进「产出」说给人听，或用元素自己的说明文字与 `questions`（每个模型文件一个数组：`{ question, answer: "", applied: false }`）。

## 一条 git 命令都不许跑

**读也不跑，写更不跑。** `git checkout`、`git restore`、`git reset`、`git stash`、`git clean` 这几条会动工作树的，一跑就可能把别人几个小时的活抹掉——项目里绝大多数时候有**没提交的改动**，那些改动只在磁盘上，git 里一份都没有，抹掉就再也回不来。`git log`、`git show`、`git diff` 这类只读的也不跑：一来它们会把上一轮已经归档、明令不许看的东西翻出来，二来你根本用不着它们。

要撤自己刚写坏的一次改动，只有一条路：**把你改的那几处按原样改回去**，或者跟开发指挥说一声、让他来处理。**别用 git 去撤**——你撤的从来不只是你那一下。

> 由来：2026-09-18，讲解为了撤自己一次写入跑了 `git checkout -- slices/k-002.story.json`，把项目所有者刚在页面上填到第 111 步的勾连同一整天未提交的走查一起退回了上一次提交。走查本身靠 scratchpad 里的备份与补丁脚本复原了，**他填的勾复不回来**。

## 不造词，不猜业务

- 模型与代码里的名词必须是 `glossary.json` 的法定名（`name`），别名只出现在注释里。需要新词的提交给业务分析（建议名 + 一行定义 + 出处），不自行写入词汇表。
- 原料里没有的，问人。同时、重复、成批这类**情形**也是业务，人说出来就记成情形语句；第一轮走主线，这类分岔不特意去问（第九十三、九十六批）。

## 边做边写细步

每做完一个小动作——新建了一个文件、改了一条规则、加了一个错误、一批测试绿了——就跑一次

```
node $DEV_TEAM/tools/scene.js <项目目录> progress <你的角色名> "<做了什么>"
```

一句话，具体到名字和从什么到什么，例如「新建错误 InvalidParticipant：五项参与者信息缺一或不像样时抛」「改 Participant 不变量 R-003：从『五样齐了』到『五项参与者信息齐了、填的都像样』」「MyAgedCareId 测试 4 个全绿」。项目所有者开着现场页看后台，没有这些他只看得见你开工了、看不见你在做什么（2026-09-13 点名）。大步（这一步在做什么、谁在干）由开发指挥写，你不写 `set`。

**这一条最常被漏掉，所以定死节奏**（2026-09-17 项目所有者：「开发指挥运行了 2 多分钟，期间没有看到 log」——那一趟之前，模型师跑了十六分钟、日志上一句没有）：

- **接活先写一句**：读完要读的原料、想清楚要动哪几处之后，写一句「这一趟打算做什么、动哪几个文件」。
- **每改完一组文件写一句**，不是攒到最后一起写。
- **一件事做得久就报一句**：翻原料、通读整个模块这种没有产出的时段，每过几分钟写一句现在翻到哪儿。
- **一句就够，别写长**（2026-09-17 项目所有者：「简要说在干什么 查什么 审什么就好」）：在干什么、查什么、审什么，落到名字上，例如「在翻手册 §13.7 找行政协调费的封顶」「在审 R-166 的落点」。不复述任务、不写心得、不列清单——细步是给人看进度的，不是交稿。
- 一趟活写几句没有定数，但**一句都没有就是漏了**：`scene back` 会算出这一趟写了几句细步、打印出来，0 句一眼看得见。

## 遇到要人裁的事当场发问，别攒到交稿

（2026-09-13 项目所有者点名。）跑一次

```
node $DEV_TEAM/tools/scene.js <项目目录> ask "<问题>" --who <你的角色名> --doing "<你当时在做什么>" --context "<上下文：牵涉到谁、哪个文件、哪一步>" --options "甲：…|乙：…" --lean "<你偏向哪个>" --confidence 高|中|低
```

五件事要说全（工具会拦：在做什么、上下文、问题、两到四个答案、你偏向哪个、信心高低），说人话、落到具体的人和事上（[wording.md](wording.md)「要人做决定的话」）。**问完照 `ask` 打印出来的那句话办**，有两种模式，哪种不用你判断，`scene ask` 会告诉你：

- **逐个**（缺省，人在电脑前）：**停下来**，把这个问题交回开发指挥，别自己替人拿主意、也别一边等一边往下写。开发指挥当场转给人，人答了会把答复送回来，你接着往下跑。
- **问卷**（人去跑长任务了）：**别停**，照你自己偏向的那个先做下去，并写一句细步说明这一处是按偏向做的（`scene progress`），交稿里也列出来。人回来一次性答，跟你偏向不一样的那几处会把你叫回来返工。

分得清什么该问：口径、范围、要不要拦、叫什么名字——这些是人的；怎么落成代码、写在哪个文件、先写哪一步——这些是你的。

**分岔不问。** 开发是迭代渐进的，第一轮只把主线（happy path）在原型上按通：守卫、重复、异常、边缘情形这类分岔，第一轮**不问、不建**，写进故事 `gaps` 标属于第几轮，等后面重新审查故事线时自然浮出来再定。只有主线走不通的事才 `ask`。分岔不是丢了：主线在原型上按通之后，人和开发指挥重审这条故事线，把 `gaps` 里标了轮次的一条条挑出来开成修改切片或下一轮的段落，模型就这样一轮一轮变健壮（2026-09-15 项目所有者：「不需要一上来就很细，我们总是去寻找 happy path 开始建立原型」「有了 happy path 的原型后，不断补充可能的其他情况，让模型健壮」）。**推后的守卫不包括方法自己的规则**（第一百六十二批）：一个方法该在什么状态下才做得、它自己的入参、它规则里写着的那句，由它自己守，第一轮照建——「属于这个行为自己的业务规则当然要自己守护」；推后的是要读别的实例才判得了的、防人手滑的。

## 写代码的角色

原型、编码**先补计划的关键逻辑、等人确认、再按计划顺序写**；每完成一步登记一次。细则在 [code/writing-code.md](../code/writing-code.md)。

## 交稿的统一格式

完成后最后一段固定为：

```
## 产出
- <写了 / 改了哪些文件，一行一个>

## 问题清单
- <要问人的事，一行一个；没有则写「无」>
```

开发指挥把「问题清单」原样汇总给人，不替人回答；汇总前给每一条标层（一层必须人裁，二层看出处，三层退回模型师）。这两段是写给不熟这套术语的人看的：先说发生了什么，再给编号。
