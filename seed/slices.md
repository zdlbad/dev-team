# 阶段与切片

*上位文档：[principles.md](principles.md)。业务分几层、怎么点亮见 [layers.md](layers.md)。这里只记思想；每一段怎么走（谁上场、做到哪停）在 `SKILL.md`「段落切片」，写入权表在 `agents/common/project-layout.md`。*

## 三个阶段

| 阶段 | 方向 | 角色 | 产出 |
|---|---|---|---|
| 一 | 业务 → 模型 | 业务分析、讲解、文职、模型师 | 全景与模块候选、按段落点亮的业务描述、词汇表、模块划分、两层模型 |
| 二 | 模型 → 代码 | 原型、接口、编码 | 代码（模型的实现，依编码规范） |
| 三 | 校验 | 模型校验、pre-pr 审查 | 报告 |

开发指挥贯穿三个阶段。阶段一是完整的建模阶段，不考虑代码；模型带着可编码的形态只是 DDD 模式的副产品。阶段二是模型的实现，编码规范在此生效。阶段三分两段：设计模型对业务描述；代码解码出的实际模型对设计模型。两段合起来即代码对业务。

**顺序是门，不是描述。** 阶段一里面业务在模型之前，这个先后写进切片记录：`stages.business` 排在 `stages.model` 之前，业务这一关不是 `done`，模型师就开不了工（`slice next` 路由回业务侧，`scene dispatch` 拒绝派模型及其下游）。业务这一关 done 的条件是范围内的语句都立好改好、且**看板上这条切片没有等人答的问题**——要人裁的事没定，下游照着建出来的多半要重来。

> 由来：2026-09-20 第一百七十八批。切片记录从前只有 `model / code / validate` 三关，模型的开工条件写的是「范围已定」，所以模型师任何时候都派得出去；段落切片靠故事点亮侥幸有道隐式的门，模块切片靠 `litAt`，**修改切片一道都没有**。那天 m-004 的三个问题只写在交接正文里、看板上一件没有，开发指挥照着往下派，业务分析先立了语句、模型校验先判了三条；他的答复一到，模型改一轮，三条判断全部重浮重填。项目所有者：「调用顺序本身是业务 → 模型，但如果没有业务的确定，上游有待定的事项，模型师本不应开工。」

## 阶段一的两种速度

```
粗读 raw ──────────────▶ 全景、模块候选（主题）、词汇表种子；不写编号语句
   ▼ 战略设计（一次，可回流）▶ 模块划分 + 模块级模型的「职责 / 关系」
   ▼ 故事线 → 段落 ────────▶ 这一段点亮的事实，归模块
   ▼ 战术・边界 ──────────▶ 这一段触及的聚合清单（名字、根、id 引用）
   ▼ 战术・内容 ──────────▶ 聚合级模型 + 模块级的「领域服务」
   ▼ 战术・编排 ──────────▶ 模块级模型的「用例」
```

| 步骤 | 速度 | 门禁 |
|---|---|---|
| 粗读 | 一次 | 人读过 |
| 战略设计 | 慢 | 单独确认；段落点亮时修正走正式回流 |
| 战术・边界（聚合清单） | 慢 | 单独确认 |
| 战术・内容（聚合级模型、领域服务） | 快 | 随段落确认 |
| 战术・编排（用例） | 快 | 随段落确认 |

模块级模型里混着两种速度：聚合清单是慢的，用例编排是快的。门禁按速度分开，不按文件分开。战略设计不是切片，是一次单独门禁。

## 五种切片

切片是迭代的步伐。

- **模块切片**（`module`，编号 k-xxx，第九十七批）：一个模块的模型，按模块一次做，只有业务与模型、不写代码。两步：**骨架初稿**（业务分析模块点亮 → 模型师一次起草全部主要聚合、实体、值对象，允许不准 → 人看模型图定初稿）→ **业务走查**（讲解出场景 → 模型师拿初稿走、长出聚合行为、改精聚合 → 人走一遍、审模型）。`pass` 标着在哪一步。见下一节「模型怎么建」。**业务走查这一步按场景切成一串，一场一条、一场一收口**（第一百五十批），见「走查一场一条」。
- **段落切片**（默认）：一段故事，单一业务意图，**只做应用层**（命令、查询、端口、`walk`）——聚合的形状与行为已在模块切片里定了。点亮 → 理解一致 → 最少模型 → 裁定 → 模型确认 → **人看模型、说出原型** → 编码计划 → 原型 → 校验 ② → 审查 → 人按。
- **演示原型这一道门**（第一百九十四批）：业务这一关收口之后、模型师开工之前，原型照走查的步骤出一叠**静态页**到 `demo/<切片>/`——一步一屏，这一步谁在哪个页面按了什么、看到什么；按钮只跳下一屏，不接模型、不写领域代码。人在工作台「演示」页按着走一遍，逻辑对了在「切片」页按「演示的逻辑对了」，模型师才开工；不对的当场说，改故事或语句再出一版。段落切片与模块切片的业务走查都要；修改、改说法、实现切片不要。已走通的也回溯补上（他答「门吧，回溯」）。为什么在建模之前：先看清人要怎么操作、再决定模型长什么样，不是先建了模型再倒回来找操作——跟「一个模块的行为哪怕没有外部模块也要独自站得住」（第一百九十二批）是一路的。
- **实现切片**：若干条已在原型上走通的段落换上生产外壳。契约 → 计划 → 外壳 → 校验 ② → 审查 → 合并。几段攒够了一起上；编码中发现模型要改的，回到那一段的切片。
- **改说法切片**（`refactor`，共用 s- 号段）：只改说法或结构、业务行为一个字不变。不走故事、不走裁定卡、不算施工单；门禁见下。
- **修改切片**（`change`，编号 m-xxx）：已走通的段落上，试原型、审阅或裁定点出的**一件事**——业务行为或模型结构要改，不是改说法。**动的是已经建好的模块就当场开、不等当前段落收口**（第一百八十四批）；要等一个还没建的模块才记候选。**一个修改切片只改一件事**；被动到的段落不重开、不改它们的阶段。
  **开出来第一件事是记一道方法块基线**：`validate --slice m-xxx --记基线`，在动手改模型之前跑。它把这一刻模块里每块方法的指纹存进切片记录，往后审模型页只摆指纹对不上的那几块——这条切片真动过的。不记，整个模块的方法就全算「他还没审过」摊开给他。
  > 由来：2026-09-20 第一百七十五批。m-004 只动了 9 块方法，审模型页摆出 67 块，项目所有者：「我发现模型页有 69 项需要我审？」——Funding 那 67 块建在 k-001，那时候逐块审还没有，一块都没人裁过，于是一块不落地全算新的。m-004 的基线是事后从 git 里补算的。
  > 由来：2026-09-14，验收项目第八十三～八十五批（拨款出处要核、语句全部重写、三条规则抽成领域服务）都没有切片记录，挂在 s-001 与 s-002 底下当「回流」——s-001 收了两次口，s-002 的模型确认、代码、计划重算了三次。项目所有者：「横切回流也是一种切片……颗粒度彻底失去了用处，现在完全是靠段落除法，随时回头，讨论范围既是修改范围了。」（第八十六批）

## 模型怎么建：先按模块起草骨架、靠业务走查长行为，故事线留给应用层

> 由来：2026-09-15 第九十五批起头，第九十七批定形。项目所有者看 s-003：「现在相当于抓住一个点就把这里的骨架和肉都实现了，后面开发与这个模块对接的内容时会出现返工的问题。」证据就在那一段里——`input.items` 的类型、AgreedPrice 三个价变四个价、ServiceAndPriceRow 十二栏至今没进模型——一个段落只看一个用例就把跨段落共享的聚合形状定死，后面碰同一个聚合的段落必然回头改。**返工的根子是形状，不是行为。** 当天他先裁了「一个段落走三遍」，夜里把前两遍改成**按模块一次做**：「为了快速铺开业务元素……按照模块，进行一次性的数据结构建模。根据业务中提到的概念和行为，进行聚合、实体、值对象的分析，一次性建立所有的主要数据结构的初稿（event、error 不用考虑）并且允许不准确，在初稿决定后进行业务走查，模拟业务，建立聚合行为，过程中可能会修改精进聚合。故事线节奏留给后面的应用层。」

三个阶段是业务分析、建立模型、写代码。建立模型分三步，前两步在**模块切片**（`k-xxx`）上按模块一次做，第三步在**段落切片**上按故事线做：

| 步 | 在哪种切片上 | 模型师建什么 | 不建什么 | 业务这边 | 代码 | 人在哪儿拍板 |
|---|---|---|---|---|---|---|
| **骨架初稿** | 模块切片 | **薄骨架**（第一百五十六批）：只列这个模块有哪几个聚合、各管什么，一句话。**允许不准，后面推翻不算错** | 守卫、不变量、行为、error、event、领域服务、命令、查询、端口；不填 `walk` | 业务分析先把这个模块的概念性语句（事实、能力）点亮一轮，`slice lit` 登记；此前模型师已做过战略设计（划上下文、划模块） | **不写** | 看模型图定初稿：哪个事实放错了聚合、哪个该拆该合。不派校验角色逐条判 |
| **业务走查** | 模块切片 | **一场一趟**（第一百五十六批）：只建这一场碰到的字段、创建、方法、不变量、领域服务、error；走不通就改聚合、拆聚合 | event、命令、查询、端口。**建立聚合、搜索聚合这类事不是聚合的行为**，`walk` 标 `leftTo: 应用`，只记下 | 讲解写走查场景（几个场景把每个概念的建立、改动、查看、结束都走到；不是故事线、不出题） | **不写** | 每一场：审这一场的走查，再按两个视角审这一场的模型（见下「模型跟着场景出」）；最后一场之后看一次整张，**模型定稿，可以出原型** |
| **应用** | 段落切片 | 命令、查询、事件处理、端口、仓储接口、event；填 `walk`、列 `choices` | — | 讲解写故事、业务分析点亮，照「每个段落」那一节 | 模型确认后**先不写**：他看一遍整个模型，说「出原型」（`slice proto-go`）才算计划、**一次写出原型**（领域层、领域服务、应用层、内存适配器、组合根、原型入口、全部测试、`walk.input`） | 审模型；出原型；确认计划；审 pre-pr；**在原型上走故事** |

四条边界，都是项目所有者定的：

- **`constructor` 也是行为，error 在走查那一步。** 初稿的值对象就是一张字段表；`CREATE` 一带守卫就得抛错，error 就被拽进初稿了，所以初稿不带守卫。
- **模型阶段一行代码都不写；应用层的模型定了、他看过说出原型，才一次写出原型，再由实现切片换生产外壳。**
  > 由来：2026-09-15 傍晚他看着 s-003 走完说：「这样一边写模型一边写代码 审代码 太慢了。把代码和模型分开吧，前期仅业务+模型，等模型定了先出原型 再代码。」证据在 s-003：一段走了 28 趟派工、他坐下 8 次，其中审计划、审 pre-pr 三轮都是代码那一侧的；模型与代码在每一段里交缠，每改一处代码就要重审一轮。夜里又加了一道门：「应用过后让我看下模型，再决定出原型。」
- **按模块做，不一次铺满全领域**——「否则战线拉得太长，因为对外模块只暴露接口」。模块之间只靠接口对接，模块内部的形状怎么定不影响别人，所以初稿的范围到模块边界为止。
- **不是所有场景都能靠聚合行为达成。** 建立聚合、搜索聚合这类操作归应用层的命令与查询，走查时认出来、记下、留给段落——不硬塞进聚合。
- **走查不走「使用上走歪」的步，也不建挡它的守卫**（第一百零一批）。
  > 由来：2026-09-16 项目所有者在手机上走 k-001 的走查，走到「页面半天没反应，李明又点了一次记录」「抄出处那一栏时手抖，填成了另一位老人的准入批准」两步：「这些故意走歪的步骤，没有必要，守卫不是现在需要的，甚至可以在打通 happy path 后在走查来补，首要任务是建立模型的结构，健壮的部分后说。当然，这是指那些系统应用的边缘场景，是使用上的，如果是业务规则上的问题，需要理清楚。」

  分界不在「这一步会不会出错」，在**错的是人还是业务**：政府拒了一行申报、余额不够只付到余额为止、一份通知书一趟批两样、比例追溯下调要退钱——业务自己就有的情形，照走照建；同一个动作点两次、抄错一栏、漏填一栏——使用上的，两边都不做，记进 `gaps`，等 happy path 打通之后另走一趟走查专门补守卫。**「一笔拨款成立要具备哪几项」这种不算使用守卫**，它说的是这样东西怎样才算数，照建。

  **行为自己的业务规则，行为自己守，不在推后之列**（第一百六十二批）。由来：2026-09-19 k-002 照七段重写，读出批准、驳回、作废都不看状态——作废了的还能批准、再作废会盖掉原来的作废原因，而业务明说作废不可撤销（R-188）。开发指挥照第一百零一批问要不要推后，项目所有者：「我之前说的并不是所有的检查都不建，这属于正常方法内的守护，属于这个行为自己的业务规则当然要自己守护」。所以**这个方法该在什么状态下才做得、它自己的入参该满足什么、它规则里写着的那句**，都是它自己的守卫，照建；推后的只是挡别处出岔的：要读别的实例、别的聚合才判得了的（一行被别的一笔占了没有、整张发票的账闭不闭合），和防人手滑的（点了两次、抄错一栏）。拿不准时问：这道检查不做，这个方法会不会亲手把自己的状态弄成业务不许的样子？会，就是它自己的。

**跟「先走 happy path」的关系**：不冲突，两者管的不是一回事。骨架先行管**形状一次定全**；happy path 是**添肉阶段**（走查、应用）的策略，管行为一轮轮变健壮——走查只建业务自己就有的那些情形，挡使用出岔的守卫连同它的场景一起留到后面，其余记 `gaps` 标轮次。**模型阶段没有可按的原型，项目所有者接受**（「我接受前期没有 prototype」）；「一段走完再开下一段」说的是应用层的段落先后。

**校验跟着步走。** 校验 ① 只查本步及之前该落的种类：骨架初稿只查事实的落点（字段）；走查加约束、公式、情形；应用全查（能力 → 命令、触发、流程）。还没到的种类不报错、单列「留给后面」，谁也别忘了它欠着。**校验 ②（代码 ↔ 模型）与 pre-pr 只在出了原型之后跑**——模型阶段没有代码，没什么可比、可审的。

## 方法怎么写：像用自然语言写一个方法

> 由来：2026-09-19 第一百五十六批。项目所有者在模型图上读 `Invoice.attachSupportingDocument`：「模型方法这里说的没有条理」「现在的版本读起来更像是在解释业务了，虽然也成立，但是缺乏条理」——五条规则用分号连成一串，谁挂、什么时候挂、方法不判的事、不记哪一栏、重录时的做法混在一起。根子在格式：一个行为只有一个 `rules`，作用、做法、规则没有各自的位置，每条业务语句又要挂到落点上，业务解释就一条条挂进了方法。第一百五十八批空跑之后，创建与领域服务的操作也照这一套写。

一个方法（行为、创建、领域服务的操作）分七段：

| 段 | 写什么 |
|---|---|
| **作用** | 调用它做了什么、改了什么，动词对得上方法名——方法名已经尽量在显式表达这个方法了，稍微丰富一下语义即可。**没有复杂逻辑的不多解释**。作用很窄的专用行为，可以再补一句它用在什么业务情形里 |
| **入参** | 每个参数是什么 |
| **做法** | 按先后写步骤，每一步改哪几栏 |
| **规则** | 这个方法自己检查什么、怎么算；不成立抛什么 |
| **错误** | 抛哪几种、各在什么时候 |
| **事件** | 发出哪几个 |
| **返回** | 返回什么 |

五条分寸：

1. **方法只写它自己守得住的。** 调用方负责的前提不写——「方法不守也守不住前提，所以方法根本不知道前提」；方法不做的事也不写。
2. **设计思路不进方法。** 「为什么不记谁传的」「为什么不认是不是同一个文件」这类，放进字段或聚合的说明。
3. **字段为什么存在写在字段的说明里**，不写在方法里。
4. **方法说明不点具体角色**；方法名里本来就带着角色、用来区分两个行为的照旧。
5. **不标简单方法，每个方法他都审**（第一百五十九批：「这样吧，都不标，我都审，之后需要再说」）。空跑时模型师把财务复核标成了简单方法，正是读了它的步骤才看出「没批准的也能复核过去」——跳过就没人看见了。

**写成一步一步，漏洞自己会显出来**：空跑里校验角色读做法读出了两处（有发票却不从发票上取录入人、复核不查批准过没有），原来那一串规则句里看不出。

格式见 `agents/model/shapes.md`「行为」。

## 模型跟着场景出，审模型分两个视角

> 由来：2026-09-19 第一百五十六批。项目所有者：「业务那侧已经定了模块下一个个场景走，太多了我一次要看 100+ 条看不过来。相应的，场景确定后，模型师是否也可以出只针对这个场景的模型，点亮聚合，虽然此时非常的不完整，但后续随着更多的场景，模型会被不断地渲染描绘变得完整。」第一百五十八批拿 k-002 的前两场空跑过：场景一要他点 9 块、场景二 3 块（新 1、重浮 2），原来一次是 38 个方法、67 条判断。

**一趟的顺序**：

0. **开工前一次，薄骨架**：模型师只列这个模块有哪几个聚合、各管什么（一句话），他在模型图上看一眼。字段、行为、规则都不预先写。**后面推翻骨架不是错误**（「不用过于担心」）。
1. 业务这一场定稿（上一节：讲解写、业务分析点亮、他审走查正文）。
2. 开发指挥点亮：这一场碰到的语句与聚合，派给模型师。
3. 模型师**只建或改这一场碰到的**，用上一节的写法，补这一场的 `walk`。**后一场只改非改不可的**：顺手改一句措辞，那一块就白白重浮、挂在那儿的判断跟着重判。
4. 工具校验：这一场的语句都要有落点；走查写着调用的方法在模型里得找得到。
5. 模型校验角色只判这一场点亮的，外加这一场改动过的那几块上原有的语句。
6. 开发指挥核一遍。
7. 出审模型页，分新的、重浮的、没变的。
8. 他审——两个视角：
   - **按模型看**：左边模型的文件夹树，右边一个文件里一个方法一块（七段）；新的与重浮的点「写得对 / 要改」，每一块都看（第一百五十九批不标简单方法）。**要改就派回模型师，改完再浮出来。**
   - **按业务看**：一条语句一张卡，落到哪几处连同模型原文摆在一起；默认只列推上来的（校验判不通过的，与重要度高、校验没把握的），他点「同意 / 不同意」。其余由工具（有没有落点）与校验角色（落得对不对、全不全）负责。
9. 要改的回到第 3 步，只重浮改过的那几块。
10. 写回（`slice apply`），这一场封口。

**最后一场之后看一次整张**：点走查的一步，亮出支撑它的聚合、方法、字段（做法里每一步记着改哪几栏，一路亮下去）。他看完，**模型就定稿，可以出原型**——「这个是审模型，模型定稿，过了这关就是可以出原型的状态了」，出原型不再是另外一关。

**头一场照样重**：头一场走主线，k-002 场景一一场就点亮了约一半的语句，而且多数落在创建上。后面的场主要是往已有的东西上添。

**「留给后面」有两种**，校验与模型师都分开说：留给**后面的场**（收据、作废这些这一场没走到的），留给**应用层**（谁来调用、查询、待办怎么摆）。

## 走查一场一条：开演前先问前提，审完就锁死

> 由来：2026-09-18 第一百五十批。项目所有者审完 k-002 的走查（120 步）之后：「另外，业务走查这里 战线拉得太长了」「一个大块 122步」。

**根子不是步数多，是一份东西同时对四拨读者负责**——他、模型师、校验器、日后接手的人。k-002 那一条里：他的勾 120 条、`walk` 一步平均 366 字（正文才 140 字）、落点 397 处、缺口 28 条、裁定卡 8 张、log 26 条，整份 153 KB 里他真正要读的只占约四分之一。而**步号是唯一的纽带，所以一动就全动**：那一天为此撞了三次（删一步后面 47 步顺延、漏网四处；插一步撞上裁定卡里混着的新旧号；他审到第 119 步推翻一条前提，整场重走还得撤他刚打的勾）。

**三条规矩**：

1. **一场一条，5–30 步。** 文件是 `slices/<模块切片id>.w<场次>.story.json`（例如 `k-003.w1.story.json`）。**步号在一场之内从 1 编起**，场与场之间不连号——这样一场里插删只动本场，别场一个字不用改。人说「我审到第几步」时带上场次。
2. **开演之前先问前提。** 每份走查文件开头一个 `premises`：这一场靠着的那几条语句（编号 + 一句人话），讲解写故事之前先摆给人确认。冲着的正是「一半的裁定攒到审走查时才出」——k-002 第一百二十批往后 30 段裁定里 15 段是他审走查时出的，其中 R-222（我方代不代付）演到第 119 步才被推翻。**先定前提，就不会演到最后才推翻。**
3. **跨场引用说事情、不说步号。** 「同第 24 步那一行路费」写成「同康宁那张发票上的护士路费」。接候选 #18、#19：指着编号的字不会自己跟着变，**指错了照样读得通，所以没人发现**。

**审完一场就锁死**（文件里 `sealed`），往后不再动那一场。锁死之后真要改，走修改切片 m-xxx（第八十六批），不回头重开那一场。

**没取的两条摆着备查**：把 `walk` 从走查里剥出去单独一份（人读的东西小四倍，可两份还是要靠步号对齐，纽带没换）；只改节奏不动结构（改动最小，可步号顺延牵连人已经打的勾这个毛病还在）。两条都与本节不冲突，日后要叠再说。

## 开发范围怎么切

> 由来：2026-09-11，项目所有者在验收项目跑到第十九批裁定时说「开发的范围太大了……人类根本消化不掉」：一处堆了七道守卫、关键逻辑 2,585 字；施工单重算三次人一次都没确认；另一条走完整条链的切片施工单 88 步。两个原因并列：**一次想的东西太多**（药是切小，本节）；**裁定答在错的层上**（药是分层，layers.md）。

**业务和模型都按段落点亮，一次只想一段。** 层级如下，业务与模型沿同一条层级往下：

| 层 | 一个单位是什么 | 业务这边 | 模型 / 代码这边 | 产出 |
|---|---|---|---|---|
| **故事线** | 完整的故事链，跑通一个多角色多模块的场景 | 从 raw 选一条线：人物、起点、终点、碰哪几个模块 | 定跨哪几个模块 | 若干段落 + 一份短索引（先后与一句衔接） |
| **段落** | **一个最小业务动作**，单一业务意图；至多两个模块，一个模块自己也算 | 点亮这一段用到的事实，归模块 | 这一段的命令与用例 | **= 一个开发切片** |
| **模块的职责** | 一个模块的一个职责 | 事实归哪个模块 | 模块内几个聚合协作 | **= 一个 PR** |
| **聚合的改动** | 一个聚合改一次 | 事实落哪个聚合、行为守哪条 | 字段、不变量、行为 | **= 一个 commit** |

段落是模块的演绎，反映落在模块上的事实。事实、段落、职责都定义一次、引用多次，不登记「谁用了我」。

**一个段落的判据**（同时满足）：

1. **单一业务意图**：切片记录里写明一句话（`intent`）。写不出一句话，就是不止一个意图。
2. **标题就是那个动作**：「上传发票源文件」「从发票录入花费」「案例经理审批花费」。哪张纸、哪一笔是例子，写在前情与步骤里，不进标题。
3. **最多两个模块**，这是上限不是门槛。三个就得再切；一个模块自己也合格，不必为了凑两个把下一段拖进来。
4. 与相邻段落的衔接**只写一句**（故事文件的 `leadsTo`），不在本段展开。

一个 **PR** = 一个模块的一个职责；施工单里属于同一个 PR 的步骤，模块必须相同。一次 **commit** = 一个聚合改一次；一步同时动两个聚合就拆成两步。

**分支按轮次进来。** 第一轮只走主线（happy path），先让原型能按；每条分支（守卫、异常、怪事）标明属于哪一轮，由后一轮的段落或修改切片带进代码。**守卫也是分支**，七道守卫一次落地就是违反这一条。一段的第一轮做完就进下一段，不在本段续深。主线按通之后重审故事线，把标了轮次的分岔一轮一轮补回来，模型是这样变健壮的，不是一上来就细（2026-09-15 项目所有者）。

**施工单的一步是增量，不是整建。** 对已存在的文件，一步写成「给 `Expense` 加 `takeFromLine` 这一个行为」，不是「建 `Expense` 聚合根，含十二条行为」。

**门禁就是门禁，不拿先例软化。** 一段施工单 ≤ 20 步、一段点亮新事实 ≤ 8、一段碰模块 ≤ 2、一次坐下裁定卡 ≤ 8（数在 `SKILL.md`「节奏」）。超了就切，不用「上一段 23 步也走通了」去说服人（2026-09-14 s-003 算出 21 步，开发指挥拿先例劝不劈，项目所有者裁劈）。

**改说法切片的门禁**，两条，第二条必须可证明：

1. 测试照旧全绿，通过数与改前一模一样，断言的业务事实（金额、GST、余额、行数、错误种类）一个都不动；跟着改名走的状态标签不算业务事实。
2. 把改名套在「改前」的解码结果上，与「改后」的解码结果逐字节比，必须一字不差（`rename-check`）。不写成「代码跟模型 0 差异」，因为模型常跑在代码前面，那时 0 差异达不到，而达不到的原因与改名无关。

## 差异回流

| 发现 | 回到 |
|---|---|
| 代码未按模型实现 | 阶段二 |
| 模型本身不对 | 阶段一（战术） |
| 业务描述有缺口或矛盾 | 阶段一（点亮那一段） |
| 触及模块划分或聚合边界 | 阶段一（战略 / 战术・边界），单独门禁 |

**切片内的轻量修正**：编码中发现的、不超出本切片范围的模型修正，模型师改，人看差异即可，不重跑校验 ①。超出范围（尤其触及边界）才升级为正式回流。段落已收口之后才发现的，不走这条：记候选、开修改切片。
