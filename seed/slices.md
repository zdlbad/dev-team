# 阶段与切片

*上位文档：[principles.md](principles.md)。业务分几层、怎么点亮见 [layers.md](layers.md)。这里只记思想；每一段怎么走（谁上场、做到哪停）在 `SKILL.md`「段落切片」，写入权表在 `agents/common/project-layout.md`。*

## 三个阶段

| 阶段 | 方向 | 角色 | 产出 |
|---|---|---|---|
| 一 | 业务 → 模型 | 业务分析、讲解、文职、模型师 | 全景与模块候选、按段落点亮的业务描述、词汇表、模块划分、两层模型 |
| 二 | 模型 → 代码 | 原型、接口、编码 | 代码（模型的实现，依编码规范） |
| 三 | 校验 | 模型校验、pre-pr 审查 | 报告 |

开发指挥贯穿三个阶段。阶段一是完整的建模阶段，不考虑代码；模型带着可编码的形态只是 DDD 模式的副产品。阶段二是模型的实现，编码规范在此生效。阶段三分两段：设计模型对业务描述；代码解码出的实际模型对设计模型。两段合起来即代码对业务。

## 阶段一的两种速度

```
粗读 raw ──────────────▶ 全景、模块候选（主题）、词汇表种子；不写编号语句
   ▼ 战略设计（一次，可回流）▶ 模块划分 + 模块级模型的「职责 / 关系」
   ▼ 故事线 → 段落 ────────▶ 这一段点亮的事实，归模块
   ▼ 战术・边界 ──────────▶ 这一段触及的聚合清单（名字、根、id 引用）
   ▼ 战术・内容 ──────────▶ 聚合级模型 + 模块级的「领域服务」
   ▼ 战术・编排 ──────────▶ 模块级模型的「用例」
```

| 步骤 | 速度 | 门禁 |
|---|---|---|
| 粗读 | 一次 | 人读过 |
| 战略设计 | 慢 | 单独确认；段落点亮时修正走正式回流 |
| 战术・边界（聚合清单） | 慢 | 单独确认 |
| 战术・内容（聚合级模型、领域服务） | 快 | 随段落确认 |
| 战术・编排（用例） | 快 | 随段落确认 |

模块级模型里混着两种速度：聚合清单是慢的，用例编排是快的。门禁按速度分开，不按文件分开。战略设计不是切片，是一次单独门禁。

## 四种切片

切片是迭代的步伐。

- **段落切片**（默认）：一段故事，单一业务意图。点亮 → 理解一致 → 五问 → 最少模型 → 裁定 → 模型确认 → 编码计划 → 原型 → 校验 ② → 审查 → 人按。**一个段落要走三遍**（骨架、行为、应用，见下一节），三遍都在同一条切片记录上，`pass` 标着现在走到哪一遍。
- **实现切片**：若干条已在原型上走通的段落换上生产外壳。契约 → 计划 → 外壳 → 校验 ② → 审查 → 合并。几段攒够了一起上；编码中发现模型要改的，回到那一段的切片。
- **改说法切片**（`refactor`，共用 s- 号段）：只改说法或结构、业务行为一个字不变。不走故事、不走裁定卡、不算施工单；门禁见下。
- **修改切片**（`change`，编号 m-xxx）：已走通的段落上，试原型、审阅或裁定点出的**一件事**——业务行为或模型结构要改，不是改说法。先记成候选、不当场改；当前段落收口后挑一件开，**一个修改切片只改一件事**；被动到的段落不重开、不改它们的阶段。
  > 由来：2026-09-14，验收项目第八十三～八十五批（拨款出处要核、语句全部重写、三条规则抽成领域服务）都没有切片记录，挂在 s-001 与 s-002 底下当「回流」——s-001 收了两次口，s-002 的模型确认、代码、计划重算了三次。项目所有者：「横切回流也是一种切片……颗粒度彻底失去了用处，现在完全是靠段落除法，随时回头，讨论范围既是修改范围了。」（第八十六批）

## 一个模块分三遍建：骨架、行为、应用

> 由来：2026-09-15 第九十五批。项目所有者看 s-003：「现在相当于抓住一个点就把这里的骨架和肉都实现了，后面开发与这个模块对接的内容时会出现返工的问题。」证据就在那一段里——`input.items` 的类型、AgreedPrice 三个价变四个价、ServiceAndPriceRow 十二栏至今没进模型——一个段落只看一个用例就把跨段落共享的聚合形状定死，后面碰同一个聚合的段落必然回头改。**返工的根子是形状，不是行为。**

上一节的梯子（边界 → 内容 → 编排）原来是在**一个段落里**一口气爬完的。现在改成**在一个模块里分三遍爬**：模块内的每个段落先都走一遍骨架，形状定全了再都走一遍行为，最后才走应用。一个段落因此会被访问三次，节奏是从骨架到肉。

| 遍 | 模型师建什么 | 不建什么 | 业务这边 | 代码 | 人审什么 |
|---|---|---|---|---|---|
| **骨架** | 实体、聚合根、值对象的**字段与类型**；聚合清单的 `members` 与 `idRefs` | 不变量、行为、创建方法的守卫、error、event、领域服务、命令、查询、端口 | 讲解写故事（只这一遍写）；业务分析点亮故事用到的语句 | **不写** | 审模型页看形状：有哪些概念、每样什么类型、住在哪个聚合 |
| **行为** | 不变量、行为（含 `CREATE` 的守卫）、error、领域服务 | event、命令、查询、端口 | 点亮本遍要落的约束、公式、情形；五问在这一遍过 | **不写** | 审模型页看行为：守卫拦什么、抛什么、判断住在哪儿 |
| **应用** | 命令、查询、事件处理、端口、仓储接口、event；填 `walk`、列 `choices` | — | 点亮能力、流程、触发 | **这一遍一次写出原型**：领域层、领域服务、应用层、内存适配器、组合根、原型入口、全部测试、`walk.input` | 审模型页看用例；确认计划；审 pre-pr；**在原型上走故事** |

三条边界，都是项目所有者定的：

- **`constructor` 也是行为，error 在第二遍。** 第一遍的值对象就是一张字段表；`CREATE` 一带守卫就得抛错，error 就被拽进第一遍了，所以骨架遍不带守卫。
- **前两遍只有业务与模型，一行代码都不写；模型定下来了，应用遍一次写出原型，再由实现切片换生产外壳。**
  > 由来：2026-09-15 当天傍晚，项目所有者看着 s-003 走完说：「这样一边写模型一边写代码 审代码 太慢了。把代码和模型分开吧，前期仅业务+模型，等模型定了先出原型 再代码。」当天早些时候他裁的是「第二遍过完写代码」，**傍晚把那一条推掉了**。证据在 s-003：一段走了 28 趟派工、他坐下 8 次，其中审计划、审 pre-pr 三轮都是代码那一侧的；模型与代码在每一段里交缠，每改一处代码就要重审一轮。分开之后，写码与审代码从**每段一次**变成**一个模块一次**，他坐下的次数按模块摊薄。
- **按模块收口，不一次铺满全领域**——「否则战线拉得太长，因为对外模块只暴露接口」。模块之间只靠接口对接，模块内部的形状怎么定不影响别人，所以骨架遍的范围到模块边界为止。

**跟「先走 happy path」的关系**：不冲突，两者管的不是一回事。骨架先行管**形状一次定全**；happy path 是**添肉阶段**（行为遍、应用遍）的策略，管行为一轮轮变健壮——第一轮只建主线的守卫与分岔，其余记 `gaps` 标轮次。**前两遍没有可按的原型，项目所有者接受**（「我接受前期没有 prototype」）；「一段走完再开下一段」在三遍里说的是同一遍之内的段落先后。

**校验跟着遍走。** 校验 ① 只查本遍及之前的遍该落的种类：骨架遍只查事实的落点（字段）；行为遍加约束、公式、情形；应用遍全查（能力 → 命令、触发、流程）。还没到的种类不报错、单列「留给后面的遍」，谁也别忘了它欠着。**校验 ②（代码 ↔ 模型）与 pre-pr 只在应用遍跑**——前两遍没有代码，没什么可比、可审的。

## 开发范围怎么切

> 由来：2026-09-11，项目所有者在验收项目跑到第十九批裁定时说「开发的范围太大了……人类根本消化不掉」：一处堆了七道守卫、关键逻辑 2,585 字；施工单重算三次人一次都没确认；另一条走完整条链的切片施工单 88 步。两个原因并列：**一次想的东西太多**（药是切小，本节）；**裁定答在错的层上**（药是分层，layers.md）。

**业务和模型都按段落点亮，一次只想一段。** 层级如下，业务与模型沿同一条层级往下：

| 层 | 一个单位是什么 | 业务这边 | 模型 / 代码这边 | 产出 |
|---|---|---|---|---|
| **故事线** | 完整的故事链，跑通一个多角色多模块的场景 | 从 raw 选一条线：人物、起点、终点、碰哪几个模块 | 定跨哪几个模块 | 若干段落 + 一份短索引（先后与一句衔接） |
| **段落** | **一个最小业务动作**，单一业务意图；至多两个模块，一个模块自己也算 | 点亮这一段用到的事实，归模块 | 这一段的命令与用例 | **= 一个开发切片** |
| **模块的职责** | 一个模块的一个职责 | 事实归哪个模块 | 模块内几个聚合协作 | **= 一个 PR** |
| **聚合的改动** | 一个聚合改一次 | 事实落哪个聚合、行为守哪条 | 字段、不变量、行为 | **= 一个 commit** |

段落是模块的演绎，反映落在模块上的事实。事实、段落、职责都定义一次、引用多次，不登记「谁用了我」。

**一个段落的判据**（同时满足）：

1. **单一业务意图**：切片记录里写明一句话（`intent`）。写不出一句话，就是不止一个意图。
2. **标题就是那个动作**：「上传发票源文件」「从发票录入花费」「案例经理审批花费」。哪张纸、哪一笔是例子，写在前情与步骤里，不进标题。
3. **最多两个模块**，这是上限不是门槛。三个就得再切；一个模块自己也合格，不必为了凑两个把下一段拖进来。
4. 与相邻段落的衔接**只写一句**（故事文件的 `leadsTo`），不在本段展开。

一个 **PR** = 一个模块的一个职责；施工单里属于同一个 PR 的步骤，模块必须相同。一次 **commit** = 一个聚合改一次；一步同时动两个聚合就拆成两步。

**分支按轮次进来。** 第一轮只走主线（happy path），先让原型能按；每条分支（守卫、异常、怪事）标明属于哪一轮，由后一轮的段落或修改切片带进代码。**守卫也是分支**，七道守卫一次落地就是违反这一条。一段的第一轮做完就进下一段，不在本段续深。主线按通之后重审故事线，把标了轮次的分岔一轮一轮补回来，模型是这样变健壮的，不是一上来就细（2026-09-15 项目所有者）。

**施工单的一步是增量，不是整建。** 对已存在的文件，一步写成「给 `Expense` 加 `takeFromLine` 这一个行为」，不是「建 `Expense` 聚合根，含十二条行为」。

**门禁就是门禁，不拿先例软化。** 一段施工单 ≤ 20 步、一段点亮新事实 ≤ 8、一段碰模块 ≤ 2、一次坐下裁定卡 ≤ 8（数在 `SKILL.md`「节奏」）。超了就切，不用「上一段 23 步也走通了」去说服人（2026-09-14 s-003 算出 21 步，开发指挥拿先例劝不劈，项目所有者裁劈）。

**改说法切片的门禁**，两条，第二条必须可证明：

1. 测试照旧全绿，通过数与改前一模一样，断言的业务事实（金额、GST、余额、行数、错误种类）一个都不动；跟着改名走的状态标签不算业务事实。
2. 把改名套在「改前」的解码结果上，与「改后」的解码结果逐字节比，必须一字不差（`rename-check`）。不写成「代码跟模型 0 差异」，因为模型常跑在代码前面，那时 0 差异达不到，而达不到的原因与改名无关。

## 差异回流

| 发现 | 回到 |
|---|---|
| 代码未按模型实现 | 阶段二 |
| 模型本身不对 | 阶段一（战术） |
| 业务描述有缺口或矛盾 | 阶段一（点亮那一段） |
| 触及模块划分或聚合边界 | 阶段一（战略 / 战术・边界），单独门禁 |

**切片内的轻量修正**：编码中发现的、不超出本切片范围的模型修正，模型师改，人看差异即可，不重跑校验 ①。超出范围（尤其触及边界）才升级为正式回流。段落已收口之后才发现的，不走这条：记候选、开修改切片。
