# 00 — 原则（骨架）

*dev-team 种子文档。只记决策，不记措辞。任何后续文档与此冲突时，以本文为准；要改，先改这里。*

## 一句话

模型驱动的开发：业务是模型的源头，模型可编码，代码可解码，校验拿两者互证。

## 骨架

1. **一个源头，两份真相，一把尺子。**
   业务描述是源头——它不与谁比对，它是被比对的依据。模型和代码是两份真相，各自可能出错。校验是尺子，只读不写。

2. **底层三元素。**
   业务描述、词汇表、模块划分。模型和代码共同遵守它们：同样的词，同样的粒度，同样的模块组织。

3. **模型可编码，代码可解码。**
   模型按 DDD 建造，因此天然可编码。代码按编码规范书写，因此可以解码还原为模型。编码规范就是这套编解码规则：正向用于写代码，反向用于从代码还原模型。规范越严，解码越准。

4. **模型 = 六边形的核心圈。**
   领域层（聚合、实体、值对象、行为、事件、错误、领域服务）+ 应用层（用例编排）。适配器与基础设施是实现，不进模型，解码时不读。

5. **模型分两层。**
   模块级（每模块一份）：职责与边界、与其他模块的关系、聚合清单及 id 引用、领域服务、用例编排。
   聚合级（每聚合一份）：实体、值对象、字段、行为及其 raises / throws、事件、错误、不变量、叙述。
   对应代码：模块级 = 一个代码模块的应用层 + 领域层目录；聚合级 = 领域层中一个聚合的内容。

6. **放置规则。**
   规则只涉及一个聚合的状态 → 聚合行为（领域层）。
   规则需同时看多个聚合 → 领域服务（领域层）。
   没有规则、只有顺序（取、调、存、发）→ 用例（应用层）。
   **用例中不允许出现业务判断。** 出现即说明有东西放错了位置。
   用例的 raises / throws 是从被调用的行为与服务镜像来的索引；真相在领域层。

7. **两速决策。**
   模块划分与聚合边界：贵、早、慢、单独门禁。
   聚合内容、领域服务、用例：便宜、晚、快、按切片。

8. **每个工件只有一个写入角色。**
   每个角色有唯一写入目标（见 [01-phases-and-slices.md](01-phases-and-slices.md)）。校验只产报告，不改任何工件。人可以直接编辑任何工件。

9. **Agent 提议，人决定。**
   每阶段末由人拍板。凡从来源无法确定的事，不猜，记为问题交给人。

10. **命名贯通。**
    词汇表是唯一命名权威。凡在模型中建了模的东西，其模型名即法定名，代码必须沿用；只有「业务里有、模型里没建」的术语才需要词汇表单独收录。

11. **结构化真相，可视化只渲染。**
    模型以 JSON 存储，供非程序员参与讨论的可视化由渲染器从结构生成。不存图代码。

12. **切片是步伐。**
    战略设计做一次；之后按故事线的段落切片，业务与模型一段一段点亮（01、07）。每个切片先定范围，再完整走三个阶段。

## 暂定（已按此写入，但可推翻）

- 战略设计（模块划分）归模型师，业务分析与人深度参与。另一种可能是归业务分析。
- 词汇表归业务分析；模型师造新词时提交收录；编码只能用不能造。
- 代码 ↔ 模型的校验：领域层是硬性的，应用层依赖放置规则的严格程度。
