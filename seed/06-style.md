# 06 — 风格：项目所有者的写法

*dev-team 种子文档。上位文档：[03-coding-standard.md](03-coding-standard.md)。本文与 03 的关系见第一节；两者冲突时**以 03 为准**。*

03 管的是**能不能解码**：它的每一条都有解码器在背后撑着，破了模型就读不回来。本文管的是**读着顺不顺**：违反了代码照跑、解码照过，但后面读代码的人要多花力气。两者是两层，不混写。

编码与原型角色两份都读；校验角色不查本文（它只比对模型与代码）；pre-pr 审查角色按本文的条目查风格。

## 二、条目

### S1 — 先想成类

领域概念是**类**，不是裸 `type`、不是对象字面量。共用的契约是抽象类（或类加不出东西时用接口）。行为挂在拥有数据的那个类上。

TypeScript 的类型层机制（联合、映射类型、条件类型）可以用，但只做 **OOP 表面之下的管道**——不拿它来表达一个领域概念。`type OrderStatus = 'draft' | 'confirmed'` 这种状态字面量联合是管道，可以；把一个聚合写成一个对象字面量加一堆自由函数，不行。

不是规则：一个类型一个文件。相关声明放一个文件里没问题。

### S2 — 数据类用经典写法

**适用范围**：03 没定形状的数据类——原型入口、契约层的 DTO、适配器内部的行数据、测试里的夹具。03 定了形状的（聚合根、实体、值对象、事件、错误、命令、查询、结果、处理器）按 03 写。

在适用范围内：私有下划线字段、构造函数里显式赋值、多行 getter；**不用构造参数属性简写**（`constructor(private readonly x: T)`）。

```ts
export class ReceiptRow {
  private readonly _sampleId: string
  private readonly _qty: number

  constructor(sampleId: string, qty: number) {
    this._sampleId = sampleId
    this._qty = qty
  }

  get sampleId(): string {
    return this._sampleId
  }

  get qty(): number {
    return this._qty
  }
}
```

不给不变的字段加 setter；外面没人读的字段不加 getter。

### S3 — 领域说业务的话，技术住在外壳里

领域层的代码读起来是业务词汇。框架 import、ORM 类型、HTTP 概念、序列化细节、传输概念都在适配器与外壳。整体上**少用框架**——领域自己拥有的一个普通类，优于一个框架抽象。

（03 第二节的 import 规则已经把这条变成了解码器可查的硬约束；本条补的是「就算 import 不违规，也别让技术词汇进领域层的命名和注释」。）

### S4 — 注册是运行时的显式动作

没有隐式的类型层注册表。凡要登记的东西（事件、处理器、订阅），**在组合根里显式登记**，完整清单在一处能读到，登记错了启动时就炸——不是编在一个封闭联合类型里，也不是靠反射或装饰器扫出来。

（03 第四节的组合根就是这个位置。）

### S5 — 该一样的行为不留开关

一件事一种做法。不加策略标志、不加开关、不加为还没到来的将来准备的选项对象。两个调用方真的需要不同行为，那是两个方法或两个类，不是一个布尔参数。

### S6 — 事件订阅者与服务长得不一样

事件订阅者接**事件对象**；服务接**普通参数**。两边共用的活抽成服务，订阅者是它上面薄薄一层。

（03 第三节：事件处理器 `handle(event)`，领域服务纯函数式接聚合与值——已经是这个形状。）

### S7 — 注释写约束，不叙述

注释讲代码的行为和原因：这个方法做什么、为什么这么做（为什么不用那个显而易见的做法、给下一个改代码的人的提醒）。不逐行复述下一行在干什么；也不写代码不负责的事——类上的注释只说这个类守的规则，要提示别处守的最多一句「唯一性不由这里守」，不加也行；上下文（并发洞、真保证在哪一层、为什么住在这里）不必写全、能不写就不写，那是模型说明文字 `note` 的事，代码不照抄（03「注释写什么」，2026-09-14 验收项目第八十七批）。

**例外**：处理器体内每条语句上方的 `//` 注释是模型里的步骤文字，解码器读它们（03 第三、五节）——那不是叙述，是模型的一部分，必须写。

### S8 — 技术基座只在一处，持久化实现只在适配器

模块内**不另设** `_shared/`：所有模块共用的技术基座只在 `src/shared/building-block/`（03 第一节）；一个模块自己的东西按 `domain / application / ports / adapters` 四个目录放。持久化实现（数据库仓储）只在 `adapters/`，端口与仓储接口留在领域层或 `ports/`。

## 三、校准

这些是**显式 OOP 的写法**，不是模仿别的语言。写惯用、可读的 TypeScript，遵守以上条目；**不发明没有条目要求的仪式**——不为每个类配一个接口、不给从不变的东西配 getter/setter 对、不搞一类型一文件、不搭工厂/建造者脚手架、不给每个类型加 `I` 前缀。条目没说到的地方，选读起来最清楚、和周围文件最像的写法。

一条风格会破坏正确性（编译不过、行为改变、丢数据）时，向人提一次，按人的裁定走。
