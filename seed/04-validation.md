# 04 — 校验规范

*dev-team 种子文档。上位文档：[00-principles.md](00-principles.md)、[01-phases-and-slices.md](01-phases-and-slices.md)。检查项的依据来自 [02-model.md](02-model.md) 第七节与 [03-coding-standard.md](03-coding-standard.md) 第六、七节。*

---

## 一、定位

- 校验**只读，只产报告**，不改任何工件；切片记录由人或流程更新。
- 两个方向：**①** 模型 ↔ 业务描述；**②** 代码 ↔ 模型（经解码）。两段合起来即代码对业务。
- 三种检查：**机械**（脚本，结果可重复）· **判断**（模型读语义，可审计）· **人确认**（校验只列出，人裁决）。
- 三级结果：**错误**（必须修）· **警告**（修掉，或由人明确驳回并留理由）· **需人确认**（人裁决）。三者未清零，切片不能完成。
- 触发：① 在建模之后、人确认模型之前；② 在编码之后；两者都可随时手动跑。
- 方向 ② 的每条差异只列两侧现状，**不判定谁对**——改代码还是改模型，由人按 01 的差异回流决定。

## 二、方向 ①：模型 ↔ 业务描述

### 覆盖（追溯的双向闭合）

| 检查 | 类型 | 级别 |
|---|---|---|
| 每条目标至少被一个命令或查询 `traces` | 机械 | 错误 |
| 每条规则按种类至少有一个落点：不变量 → `invariants` 或行为 `throws`；反应 → 事件处理 `trigger`；推导 → 行为 `rules` | 机械 | 错误 |
| 每个模型元素 `traces` 非空，且编号在业务描述中存在 | 机械 | 错误 |
| 落点的文本确实表达了那条语句（不是挂了编号就算） | 判断 | 警告 |
| 业务描述里的名词在词汇表和模型里都找不到 | 判断 | 警告 |

### 命名

| 检查 | 类型 | 级别 |
|---|---|---|
| 每个模型名是词汇表中的词 | 机械 | 错误 |
| 词汇表中的词在模型里以别名出现（同义词漂移） | 判断 | 警告 |

### 模型内部一致性

| 检查 | 类型 | 级别 |
|---|---|---|
| 每个步骤的 `call` 解析到存在的目标与方法 | 机械 | 错误 |
| 用例 `raises` / `throws` = 所调行为与服务之并集 | 机械 | 错误 |
| 每个事件、每个错误至少有一个发布方 | 机械 | 错误 |
| 每个事件处理的 `trigger` 解析到存在的事件 | 机械 | 错误 |
| 查询只调仓储 `read` 方法 | 机械 | 错误 |
| 处理器步骤的 `behavior` 目标只能是聚合根 | 机械 | 错误 |
| `when` 只引用前面某步领域调用的 `output` | 机械 | 错误 |
| 领域服务 `coordinates` 只含本模块聚合 | 机械 | 错误 |
| 跨模块引用只出现在 `ports` 与事件处理 `trigger` | 机械 | 错误 |
| `module.json` 聚合清单与 `domain/` 文件夹一致；`members` 与实体 / 值对象文件一致 | 机械 | 错误 |
| `idRefs` 指向存在的聚合 | 机械 | 错误 |
| 命令 `writes` = 步骤实际写入之并集 | 机械 | 错误 |
| 命令或事件处理 `writes` 长度 > 1 | 人确认 | 附四条出路：合并 / 抽第三个聚合 / 最终一致 / 承认例外 |
| 一个事件没有任何处理者 | 机械 | 警告（可能是终止事件） |
| 用例步骤 `text` 里藏着业务判断（放置规则违规） | 判断 | 警告 |
| 一条不变量实际跨两个聚合（边界信号） | 判断 | 需人确认 |

## 三、方向 ②：代码 ↔ 模型

### 前置：解码

- 解码器按 03 第六节产出 `model-decoded/<version>/`。
- 03 第七节的十六条禁止项在解码时作为 lint 报告，全部是**错误**。
- 结构无法识别、解码失败的文件单独列出，是错误。

### 比对（按文件一一对应）

| 差异 | 类型 | 级别 |
|---|---|---|
| 模型有、代码无（未实现） | 机械 | 错误 |
| 代码有、模型无（未设计的新增） | 机械 | 错误 |
| 字段、行为签名、事件 payload、仓储方法、端口操作不一致 | 机械 | 错误 |
| `raises` / `throws` / `writes` / `trigger` / `reads` 不一致 | 机械 | 错误 |
| 步骤序列不一致：先按 `call` 匹配，再比 `when` | 机械 | 错误 |
| `traces` 不一致 | 机械 | 错误 |
| 步骤 `text`、`rules`、`invariants`、`narrative` 文字不同 | 判断：语义等价则通过，否则警告 | 警告 |
| 类型映射差异（`date` 对 `Date`、模型名对带后缀类名） | 机械，容差内忽略 | — |

### 盲区（报告里固定声明）

错误的 `condition`、实体封装的运行时行为、适配器的正确性、测试的充分性——校验不覆盖，靠测试与普通代码审查。

## 四、判断的可审计性

判断类检查依赖模型读语义，不可重复。为了不漏细节，判断不是黑盒：

**穷尽而非抽样。** 判断按对象逐个做——每条追溯链接、每个步骤文本、每条规则文本。判断日志头部写明「已判断 N / N」。

**每次判断记一条**，不论结论是通过还是不通过：

```jsonc
{ "target": "aggregate-root.OrderAggregateRoot.json#behaviors.confirm.rules[0]",
  "check": "模型规则是否与业务一致？",
  "sides": { "business": "[R-001] 预算总额不得超过核定额度", "model": "确认时校验总额 ≤ 核定额度" },
  "verdict": "pass",                 // pass | fail
  "importance": "high",              // high | medium | low
  "confidence": "high",              // high | medium | low
  "reason": "一句话" }
```

**重要度**按离领域的距离：

| 级别 | 对象 |
|---|---|
| 高 | 聚合不变量、行为规则、值对象、错误、事件 |
| 中 | 用例步骤、事件处理、领域服务操作 |
| 低 | 端口、词汇表别名、叙述文字 |

**自信度**三级，必附一句理由。

**升级规则**：
- 重要度高 + 自信度非高 → 自动升为**需人确认**，不论 verdict
- 重要度低 + 自信度高 + verdict 为 pass → 只记日志，不进警告
- 其余 → 按检查项本身的级别

**排序**：判断日志按重要度降序、自信度升序排列，人从「最重要且模型最没把握」的那条看起。

**审阅方式**：判断与需人确认项按「业务 → 模块 → 聚合」的顺序逐条呈现，通过**审阅工具**完成：本地 Node 起一个页面，渲染报告 JSON，人逐条填入裁决与备注，保存回 JSON，agent 读取后继续。同一工具也用于切片的模型确认。

## 五、报告

**不留历史。** `reports/` 每个方向只留最新一份，覆盖：`reports/validate-1.json` / `.md`、`reports/validate-2.json` / `.md`。报告是临时物，可被遗忘。

**结论记到目标本身，不记在报告里：**
- 驳回的警告、接受的多聚合 `writes`、边界信号的裁定 → 目标模型文件的 `decisions[]`（形状见 02 通用约定）
- 业务层面的结论 → 业务描述中的一条语句
- 校验器读 `decisions[]`，按 `on`（对象文字的哈希）判断是否变化：未变化的项不再重复提出，变化了的项带着上次裁决（`staleDecision`）重新提出
- 只有「不需要改」的裁决才写回：判断通过且人同意 → `dismissed`；承认例外 / 接受现状 → `accepted`（必须写理由）；驳回的警告 → `dismissed`。「需要改」的裁决不写回，列为回流清单记入切片记录
- 变化的追溯靠 git：每个项目一个文件夹、一个仓库

```
概要        切片 · 方向 · 解码版本（方向 ②）· 错误 / 警告 / 需人确认 数 · 判断已做 N / N · 结论
错误        逐条：位置（文件 / 元素）· 检查项 · 说明 · 两侧现状
警告        同上
需人确认    逐条：说明 · 选项（如 writes 的四条出路）· 来源（规则 / 判断升级）
判断日志    全部判断，按重要度降序、自信度升序
盲区        固定声明
结论        干净 / 不干净；不干净时列出阻止切片完成的错误编号
```

「干净」= 零错误、零未处理警告、零未裁决的需人确认。
