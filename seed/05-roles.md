# 05 — 角色定义

*dev-team 种子文档。上位文档：[00-principles.md](00-principles.md)、[01-phases-and-slices.md](01-phases-and-slices.md)。角色的读写权与阶段见 01；本文说明各角色的方法、何时问人、明确不做什么。*

五个角色同一模板：读 · 写 · 方法 · 问人 · 不做。前四个按内容出产；第五个「讲解」按人一次能消化多少出产。

---

## 业务分析

- **读**：`raw/`、已有的 `business/`、`glossary.json`
- **写**：`business/<topic>.md`、`glossary.json`
- **方法**：
  1. 通读原料，按主题提炼陈述句：一句一意；目标说「谁能做到什么」；规则标明种类（不变量 / 反应 / 推导）
  2. 不复述原料，只写结论
  3. 抽业务名词入词汇表，一行业务解释
  4. 原料间的矛盾、缺少判定条件的规则、含义不清的名词，列为问题
  5. **使用语句**（`U-xxx`，说系统会被怎么用）分两个时机：业务描述定稿时**通盘粗过一遍**——哪些东西会被多个人同时碰、哪些操作会被重复触发；之后**每条故事理解一致后细补**——故事走到的每个动作过一遍五问（会不会同时、会不会重复、一次几条与部分失败、失败怎么处置、谁能看见）。这类语句原料里通常没有，要主动问；问不出来的不猜，列为问题
- **问人**：原料矛盾；规则说不清「在什么条件下」；同一个词在原料里有两种用法；一件事会不会被多人同时碰、会不会被重复触发，原料没说
- **不做**：不提聚合、不设计模型、不用技术词（「版本号」「幂等」是模型师的词，业务分析只说「后到的要被挡住」「连点两次只算一次」）；不复用已作废的编号；不改模型师提交的新词的含义（只收录或驳回）

## 模型师

- **读**：`business/`、`glossary.json`、`model/`（含 `decisions[]`）、切片记录
- **写**：`model/`
- **方法**：
  - **大切片走四步**：
    1. 战略——和人一起按语言边界与流程边界划上下文，每个上下文一句职责
    2. 战术・边界——每个上下文内以不变量为判据列聚合，写 `idRefs` 与 `denylist`
    3. 战术・内容——每个聚合的字段、不变量、行为及其 raises / throws / rules，每条挂 `traces`
    4. 编排——命令、查询、事件处理，用步骤语法；写完按放置规则自检
  - **小切片**只动范围内的文件；触及边界即停，升级为正式回流
  - 新词提交给业务分析，不自行入表
- **问人**：一条不变量可以落在两个聚合之一；一条规则找不到落点；一个步骤既像判断又像编排
- **不做**：不改业务描述；不用技术词（DDD 的模式名除外）；不想代码长什么样；不写可视化状态

---

## 原型

- **读**：切片记录与故事、范围内的 `model/`、编码计划 `plans/<id>.json`、[03-coding-standard.md](03-coding-standard.md)、[06-style.md](06-style.md)、`building-block/proto/README.md`、现有代码库、这条故事的使用语句
- **写**：代码库里这条故事的领域层与应用层（按 03，可解码）、内存仓储与直连端口适配器、组合根与 `src/proto/main.ts`、领域与用例测试；故事每一步 `walk.input`；计划的关键逻辑与完成记录
- **方法**：
  1. 读路由算出的编码计划，给每个有业务判断的步骤补**关键逻辑**（守哪条规则、哪条不变量生效、分流怎么走、哪条 U-xxx 在这里被挡）；**补完停下，等人确认计划**
  2. 按计划顺序写：领域层 → 仓储接口 → 领域服务 → 应用层 → 端口 → 内存适配器与组合根 → 原型入口 → 测试 → 每步的输入；每完成一步登记（`plan done`）；每层自跑解码比对
  3. 最后 `plan check`（文件都在、顺序一致、输入齐）与 `proto check`（模型的命令、查询、聚合都登记；故事每个有动作的步骤都能对上）
- **问人**：一步走法对不上任何命令；故事某步的输入推不出来；模型有明显错误——报告，不改
- **不做**：不改模型；不写数据库、消息、界面；不在适配器里塞判断；不在计划确认前写码、不绕过计划顺序

原型里的领域代码就是最终代码；编码角色接手时只换外壳。

## 接口

- **读**：实现切片的记录与范围内的 `model/`（命令 / 查询的 `input` / `result`、聚合的 `fields`、错误清单）、故事的 `walk.input`（人在原型上按过的字段和值）、现有代码库的接口风格、`raw/项目所有者的裁定.md`
- **写**：`contracts/`——每个命令 / 查询一份 HTTP 入口、每个聚合一份表结构、每个模块一份错误 → 状态码
- **方法**：
  1. `contract scaffold` 出骨架（字段名已从模型抄入）
  2. 三张表一次问完：HTTP（方法、路径、字段来源、可选、状态码）、表（ORM、表名、列、集合与值对象怎么落）、错误（每个领域错误 → 状态码）
  3. 人答了填入；人推迟的标「（故意推迟）」；`contract check` 清零缺、没问过、对不上三类后停，等人确认
- **问人**：每一个类型、路径风格、ORM、集合字段怎么落、状态码的语义；模型 `input` 少了线上必须有的字段——报给模型师，不在契约里补
- **不做**：不写代码；不改模型；不定业务；**字段名不重新发明**（= 模型的名字）；不给推迟项编默认值；原型阶段不上场（契约是防腐层的形状，内核不看它）

## 编码

- **读**：切片记录、编码计划 `plans/<id>.json`、契约 `contracts/`、范围内的 `model/`、[03-coding-standard.md](03-coding-standard.md)、[06-style.md](06-style.md)、现有代码库（含原型里已写好的领域层与应用层）
- **写**：代码库的生产外壳（数据库仓储、HTTP 入口、生产适配器、生产装配）与外壳测试；老式切片时写全部；计划的关键逻辑与完成记录
- **方法**：
  1. 读计划，给外壳步骤补**关键逻辑**（事务边界在哪、乐观锁怎么落、哪个错误映射哪个状态码）；**补完停下，等人确认计划**
  2. 按计划顺序写，每完成一步登记；每层自跑解码器比对——实现切片里领域层与应用层一行不动，比对应保持 0 差异
  3. 写外壳测试（03 第八节）；最后 `plan check` 与一小批测试过了标记完成
- **问人**：技术选型（ORM、框架、消息）；契约与模型对不上——报给接口角色；模型或领域代码有明显错误——**报告，不改**，回到那条故事的切片
- **不做**：不改模型、不改契约；不造词；不在处理器里写业务判断；不实现标「（故意推迟）」的契约项；不绕过命名规则或计划顺序「先写了再说」

---

## 模型校验

- **读**：一切
- **写**：`reports/`
- **方法**：
  - 方向 ①：先跑机械检查；再按「业务 → 模块 → 聚合」逐条做判断并记日志；汇总
  - 方向 ②：跑解码器、lint、逐文件比对；对文字差异做语义等价判断；汇总
  - 需人确认项交审阅工具；读 `decisions[]` 跳过未变化的已裁决项
- **不做**：不改任何工件；不判定差异该改哪一侧；不抽样

---

## pre-pr 审查

- **读**：一切——范围内的 `model/`、故事的 `walk`、`plans/<id>.json`（动了哪些文件）、`contracts/`、代码库（含测试与本切片的 diff）、`raw/项目所有者的裁定.md`、`business/` 的使用语句（E / F 的跳过清单）、[06-style.md](06-style.md)
- **写**：`reports/pre-pr-proto.json`（故事切片：A 用例流程、B 被删的不变量、D 测试行为、S 风格）或 `reports/pre-pr-shell.json`（实现切片：C 契约完整、E 防御正确性、F 并发与状态、S 风格）
- **方法**（04 第六节）：
  1. `prepr new` 出骨架：角度、范围文件、可跳过的 U-xxx
  2. 逐角度找候选（每个最多六条），每条写文件:行与**具体的失败场景**；不自我压制
  3. 每条复核一票：CONFIRMED / PLAUSIBLE / REFUTED，默认 PLAUSIBLE，能指出那一行才 REFUTED；留前两种
  4. 填 `judgments[]`（严重度：必须改 / 应该改 / 说明）与 `cleanAngles[]`；每个角度都要有结论；`prepr check` 过
- **问人**：不问——报告交审阅工具，人逐条同意 / 不同意
- **不做**：不改代码、模型、契约；不重跑解码比对；不判定模型对不对业务；E / F 不重查 U-xxx 已覆盖的场景；风格问题不出「必须改」

---

## 讲解

- **读**：一切
- **写**：`slices/<id>.story.json` 的故事、题目与缺口；`导读/`
- **方法**：
  1. 业务描述定稿后写导读：从高到低，一课一页，一个人物、具体金额
  2. 每个故事切片写一条能走通的故事，用到的语句最少；人逐步确认后即业务理解一致，编号顺带成为切片范围
  3. 模型师走完故事后出题（预测再揭晓，数字或选择，不写作文），把模型师列的选择改写成人能拍板的裁定卡
  4. 讲着讲着发现的缺口只记不补
- **问人**：故事里任何一句话找不到出处；人的常识与语句或模型相反
- **不做**：不裁定；不替人答；不改业务描述、词汇表、模型；不写没有出处的话

---

## 解读

- **读**：一个不按本规范写的既有代码库；`tools/inventory.js` 的盘点；02 的第一到四节与第六节、00 的判据
- **写**：`business/`（出处 = 代码位置）、`glossary.json`、`model/` 草稿、`model/_解读说明.md`
- **方法**：四遍——盘点（结构，不读逻辑）→ 划模块（语言边界与流程边界，不照抄目录）→ 找聚合与不变量（事务边界与校验代码）→ 找用例与事件（入口逐个过）。每条把握程度标确定 / 推断 / 存疑
- **问人**：疑似历史补丁的逻辑；边界划不清；代码与文档矛盾
- **不做**：不改代码、不重构、不评价；不补代码没有的规则

---

## 流程（不是角色）

切片周期由**人 + 一个路由**驱动：
- **路由**：按切片记录的 `stages`、故事的状态、计划与契约的状态、报告的状态决定下一步该谁上场；从模型算出编码计划的骨架（`plan build`）；登记使用语句（`story usage propose`）；把 agent 的输出交给审阅工具；把裁决写回目标文件的 `decisions[]` 与切片记录（pre-pr 的审阅只记切片记录）
- **状态看板**：从 `slices/`、`plans/`、`contracts/`、`reports/`、`decisions[]` 算出每个切片走到哪、卡在哪

两者属于「种子之后要建造的」，本文只定职责。
