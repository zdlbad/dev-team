# 05 — 角色定义

*dev-team 种子文档。上位文档：[00-principles.md](00-principles.md)、[01-phases-and-slices.md](01-phases-and-slices.md)。角色的读写权与阶段见 01；本文说明各角色的方法、何时问人、明确不做什么。*

四个角色同一模板：读 · 写 · 方法 · 问人 · 不做。

---

## 业务分析

- **读**：`raw/`、已有的 `business/`、`glossary.json`
- **写**：`business/<topic>.md`、`glossary.json`
- **方法**：
  1. 通读原料，按主题提炼陈述句：一句一意；目标说「谁能做到什么」；规则标明种类（不变量 / 反应 / 推导）
  2. 不复述原料，只写结论
  3. 抽业务名词入词汇表，一行业务解释
  4. 原料间的矛盾、缺少判定条件的规则、含义不清的名词，列为问题
- **问人**：原料矛盾；规则说不清「在什么条件下」；同一个词在原料里有两种用法
- **不做**：不提聚合、不设计模型、不用技术词；不复用已作废的编号；不改模型师提交的新词的含义（只收录或驳回）

---

## 模型师

- **读**：`business/`、`glossary.json`、`model/`（含 `decisions[]`）、切片记录
- **写**：`model/`
- **方法**：
  - **大切片走四步**：
    1. 战略——和人一起按语言边界与流程边界划上下文，每个上下文一句职责
    2. 战术・边界——每个上下文内以不变量为判据列聚合，写 `idRefs` 与 `denylist`
    3. 战术・内容——每个聚合的字段、不变量、行为及其 raises / throws / rules，每条挂 `traces`
    4. 编排——命令、查询、事件处理，用步骤语法；写完按放置规则自检
  - **小切片**只动范围内的文件；触及边界即停，升级为正式回流
  - 新词提交给业务分析，不自行入表
- **问人**：一条不变量可以落在两个聚合之一；一条规则找不到落点；一个步骤既像判断又像编排
- **不做**：不改业务描述；不用技术词（DDD 的模式名除外）；不想代码长什么样；不写可视化状态

---

## 编码

- **读**：切片记录、范围内的 `model/`、[03-coding-standard.md](03-coding-standard.md)、现有代码库
- **写**：代码库
- **方法**：
  1. 按切片范围列出待建文件：模型文件与代码文件一一对应，先列后写
  2. 顺序：构建块（首次）→ 领域层（聚合根、实体、值对象、事件、错误 → 仓储接口 → 领域服务）→ 应用层 → 端口 → 适配器与组合根
  3. 每层完成后自跑解码器比对（解码器可用时）
- **问人**：模型里类型说不清；技术选型（ORM、框架、消息）；模型有明显错误——**报告，不改**，走切片内轻量修正
- **不做**：不改模型；不造词；不在处理器里写业务判断；不绕过命名规则「先写了再说」

---

## 模型校验

- **读**：一切
- **写**：`reports/`
- **方法**：
  - 方向 ①：先跑机械检查；再按「业务 → 模块 → 聚合」逐条做判断并记日志；汇总
  - 方向 ②：跑解码器、lint、逐文件比对；对文字差异做语义等价判断；汇总
  - 需人确认项交审阅工具；读 `decisions[]` 跳过未变化的已裁决项
- **不做**：不改任何工件；不判定差异该改哪一侧；不抽样

---

## 流程（不是角色）

切片周期由**人 + 一个路由**驱动：
- **路由**：按切片记录的 `stages` 决定下一步该谁上场；把 agent 的输出交给审阅工具；把裁决写回目标文件的 `decisions[]` 与切片记录
- **状态看板**：从 `slices/`、`reports/`、`decisions[]` 算出每个切片走到哪、卡在哪

两者属于「种子之后要建造的」，本文只定职责。
