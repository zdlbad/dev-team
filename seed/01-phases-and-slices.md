# 01 — 阶段与切片

*dev-team 种子文档。上位文档：[00-principles.md](00-principles.md)。*

## 三个阶段

| 阶段 | 方向 | 角色 | 产出 |
|---|---|---|---|
| 一 | 业务 → 模型 | 业务分析、模型师 | 业务描述、词汇表、模块划分、两层模型 |
| 二 | 模型 → 代码 | 编码 | 代码（模型的实现，依编码规范） |
| 三 | 校验 | 模型校验 | 报告 |

阶段一是完整的建模阶段，不考虑代码；模型带着可编码的形态只是 DDD 模式的副产品。
阶段二是模型的实现，编码规范在此生效。
阶段三分两段：设计模型对业务描述；代码解码出的实际模型对设计模型。两段合起来即代码对业务。

## 阶段一的内部结构

```
业务描述
   │
   ▼ 战略设计 ─────────▶ 模块划分（底层）+ 模块级模型的「职责 / 关系」
   │
   ▼ 战术・边界 ────────▶ 模块级模型的「聚合清单」（名字、根、id 引用）
   │
   ▼ 战术・内容 ────────▶ 聚合级模型（实体、值对象、行为、事件、错误）+ 模块级的「领域服务」
   │
   ▼ 战术・编排 ────────▶ 模块级模型的「用例」
```

| 步骤 | 写入 | 速度 | 门禁 |
|---|---|---|---|
| 战略设计 | 模块划分；模块级模型的职责 / 关系 | 慢 | 单独确认 |
| 战术・边界 | 模块级模型的聚合清单 | 慢 | 单独确认 |
| 战术・内容 | 聚合级模型；模块级的领域服务 | 快 | 随切片确认 |
| 战术・编排 | 模块级模型的用例 | 快 | 随切片确认 |

模块级模型里混着两种速度：聚合清单是慢的，用例编排是快的。门禁按速度分开，不按文件分开。

## 切片

切片是迭代的步伐。初次建模是一个**大切片**（四步走全）；之后的迭代是**小切片**（多数只动战术层，偶尔触发战略层修订）。

切片首先是对**模型改动范围**的定稿；然后在范围内完成编码与校验。

### 故事切片

按主题划范围的初始切片对模型师是一次任务，对人是一堵墙：几十条语句、几个聚合、几十个文件一次建完，人没有位置参与，只能事后补课。所以战术设计按**故事**切：

- 战略设计仍通盘做（模块划分便宜、稳定，单独门禁）。
- 之后每个切片是**一条能从头走到尾的故事**：一个人物、按日期排的步骤、具体金额、每步用到的语句编号。第一条永远是这门生意最贴近日常的主线，不是最全的。
- 故事由讲解角色写，人逐步读、逐条确认语句、同意或质疑——**这一步是在业务理解上达成一致**，不是在划范围；一致之后它的编号顺带成为切片范围。
- **使用语句**：理解一致之后、建模之前，业务分析把故事走到的每个动作过一遍五问（会不会同时、会不会重复、一次几条与部分失败、失败怎么处置、谁能看见），新增的写成 `U-xxx`（02 第一节），人确认后并入切片范围。这类语句原料里通常没有，模型却必须回应（版本号、状态守卫、部分失败的语义）——校验 ① 查落点，人在原型上按出来。通盘的一遍（哪些东西会被多人同时碰）在业务描述定稿时先做，细的按故事补。
- 模型师只建走通这条故事所需的最少模型，建完在故事上走一遍（每步对应哪个命令、动了哪个聚合），并把做过的选择列成裁定卡；讲解出题；人预测再揭晓、过裁定卡；裁定与模型现状不同的回流模型师。
- 之后才轮到校验角色填判断、人审阅、模型确认。
- **编码计划**：模型确认后、写码之前，路由从模型算出这次要动哪些代码文件、按什么顺序（`plans/<id>.json`，被引用的聚合先建、再仓储接口、再服务、再用例、再端口、再适配器与装配、再测试）；写码的角色在每一步下面补**关键逻辑**（守哪条规则、哪条不变量在这里生效、分流怎么走）；**人确认后才开写**，写的时候每完成一步登记一次，写完核对文件都在、顺序与计划一致。原型与外壳两次都有计划、都要人看；外壳那一次更值得细看——事务、锁、状态码模型里没有，全靠计划。
- **原型**：原型角色按计划把这条故事变成能按的东西——领域层与应用层按编码规范写（这就是最终代码），仓储与端口用内存适配器，装进原型宿主，领域与用例测试一起写；校验 ② 干净后 **pre-pr 审查**查 A 用例流程 / B 被删的不变量 / D 测试行为 / S 风格（04 第六节）——领域代码刚写完最便宜；然后人打开页面按故事走，随手改输入看规则怎么拒，试 U-xxx 说的连点、同时、成批。**每条故事都反映在原型上**，原型是人对模型的最后一道检查，也是代码的第一层。
- **实现切片**另起：指定若干条已在原型上走通的故事（`--implements`），范围从它们走过的聚合与用例推出。先由**接口角色**把外壳的契约钉死（`contracts/`：每个命令 / 查询的 HTTP 入口、每个聚合的表结构、每个模块的错误 → 状态码；字段名沿用模型，类型不确定就问人，没问过的与故意推迟的分开标），人确认；再出外壳的编码计划，人确认；编码角色只补生产的外壳（数据库、消息、接口），领域代码不重写；校验 ② 仍须 0 差异；pre-pr 审查查 C 契约完整 / E 防御正确性 / F 并发与状态 / S 风格。几条故事攒够了一起上。编码中发现模型要改的，回到那条故事的切片。
- **故事按版本滚雪球**：第一条是最小的能走通的主线；之后每条故事基于上一条（`basedOn`），只多一段（`adds`）——一个缺口、一件怪事、一段前情。老步骤原样保留，新段插进去，整条从头再走通；模型只加新段需要的最少部分，但每一步都重走，保证老路没断。上一版的缺口就是下一版的候选，人勾选。框架图按谱系列故事，标出每版比上一版新点亮的域与数量。

人参与三次，每次一页纸。模型的概念是一片一片攒起来的，不是最后补课。故事文件的形状见 `schema/story.schema.json`，驱动见 `tools/story.js` 与 `tools/slice.js`。

### 一个切片的周期

1. **定范围**：人与模型师商定本轮模型改动范围，写下切片记录。
2. **建模 / 改模**：模型师在范围内工作。遇到业务不清 → 业务分析回原料找；找不到 → 问人。业务描述有缺口时先补业务描述，模型再跟进。
3. **校验 ①**：模型对业务描述 → 报告。
4. **人确认模型**（门禁；触及模块划分或聚合清单的变动单独确认）。
5. **编码**：按编码规范从模型实现。
6. **校验 ②**：解码代码得到实际模型，与设计模型比对 → 差异报告。
7. **处理差异**：代码错 → 回 5；模型错或业务缺口 → 回 2。
8. 校验干净 → 切片完成，人合并。

### 差异回流

| 发现 | 回到 |
|---|---|
| 代码未按模型实现 | 阶段二 |
| 模型本身不对 | 阶段一（战术） |
| 业务描述有缺口或矛盾 | 阶段一（业务描述） |
| 触及模块划分或聚合边界 | 阶段一（战略 / 战术・边界），单独门禁 |

### 切片内的轻量修正

编码中发现的、**不超出本切片范围**的模型修正：模型师改，人看差异即可，不重跑校验 ①。超出范围（尤其触及边界）才升级为正式回流。

## 角色与写入权

| 角色 | 阶段 | 唯一写入目标 | 不得写 |
|---|---|---|---|
| 业务分析 | 一 | 业务描述（目标、规则、使用语句）、词汇表 | 模型、代码 |
| 讲解 | 一（贯穿） | 故事（人物、步骤、题目、缺口）、导读 | 业务描述、词汇表、模型 |
| 模型师 | 一 | 模块划分、两层模型；故事的 `walk` 与 `choices` | 业务描述（提交问题）、词汇表（提交新词）、代码 |
| 原型 | 一→二 | 故事的领域层、应用层、内存适配器、组合根、原型入口、领域与用例测试；故事的 `walk.input`；计划的关键逻辑与完成记录 | 模型（报告不一致）、词汇表、契约 |
| 接口 | 二（实现切片开头） | 契约 `contracts/` | 代码、模型、业务描述 |
| 编码 | 二 | 生产外壳与外壳测试；计划的关键逻辑与完成记录 | 模型（报告不一致）、词汇表、契约（报给接口角色）、领域层与应用层（回到故事切片） |
| 模型校验 | 三 | 校验报告 | 一切工件 |
| pre-pr 审查 | 三 | 审查报告 | 一切工件 |
| 解读 | 零 | 业务描述、词汇表、模型草稿、解读说明 | 代码 |

路由写切片记录、编码计划的骨架（`plans/`）与模型文件的 `decisions[]`。人在每个阶段末拍板，并可直接编辑任何工件。
