# 业务描述

`raw/` 是原料；业务按场景里问到的逐条立成语句，分层与种类见 dev-team 的 `agents/business/layers.md`。

- `全局图.json`、`故事/`、`概念/`：给人建立业务理解的三样——业务分几块（`agents/business/concepts.md`「全局图」）、最主要的几段事怎么走（`agents/business/stories.md`）、一个概念是什么和跟别的东西什么关系（`agents/business/concepts.md`「概念」），故事、概念人在工作台上定下；不写别的文章
- `<主题>/abstraction.md`：第一层，手册层面的抽象业务（换一家公司照样成立）
- `<主题>/practice.md`：第二层，这家公司的做法，含五问问出来的情形

主题是业务里叫得出名字的东西（参与者、服务协议），一个主题一个文件夹，不跟模块。

陈述性语句，正向陈述，一句一个业务动作，每条标出处；编号按点亮顺序发，永不复用。编号后面跟 `(层-种类)` 标签：层是业务抽象或业务落地，种类是能力 / 事实 / 约束 / 公式 / 触发 / 流程 / 情形。文件内按能力 / 规则分节：

```markdown
## 能力
- [G-001] (业务抽象-能力) 协调员能为参与者制定预算

## 规则
- [R-001] (业务抽象-约束) 预算总额在参与者的核定额度之内
- [R-003] (业务抽象-公式) 剩余额度 = 核定额度 − 已分配
- [R-002] (业务落地-触发) 预算被批准后，服务提供方收到通知
- [R-004] (业务落地-情形) 同一份预算可能由两位协调员先后经手
```

五问（会不会同时、会不会重复、一次几条、失败了业务上怎么办、谁能看见）由业务分析在每段点亮时主动问，问出来的情形（可能碰上的情况）写成普通语句、种类标「情形」；软件怎么回应（只算一次、幂等、锁）归模型师，不进这里。
